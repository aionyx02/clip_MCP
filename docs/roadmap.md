# Roadmap — clip-mcp 2.0

**這份文件只留還沒做的事，以及刻意不做的事為什麼不做。** 已經落地的東西寫在
`architecture.md`，不在這裡重述。

## 現況

**功能章節（§1–§10）全部做完了。** 剩下的只有兩件，而它們其實是同一件事：

- **§11 Benchmark**——用真實素材證明剪得好不好。這是**下一個工作項目**。
- **§13 等語料才能決定的數字**——每一個都是 §11 要回答的問題。

2.0 的核心想法——把剪輯決策變成被持久化的資料——已經落地成：語意時間軸、段落與主題、
剪輯計畫與編譯器（含四個清理階段、B-roll、分段配樂與對拍、節奏設定）、出身與鎖定、
plan 的版本歷史、素材量測（畫面、聲音、人臉、跨檔案的說話者、配樂節拍）、
時間軸（J/L cut、三種轉場、變速與音高、段落標記）、字幕（平台樣式、逐字、雙語、講者）、
聲音（語音修復、逐講者響度）、預覽（增量、差異、聲音）、輸出（多比例跟臉重構圖、
出片前檢查、章節、封面、EDL/OTIO/FCPXML）。

benchmark 排在最後是刻意的：評測要量的東西得先存在，功能還在長的時候量出來的分數，
幾個月後已經不是同一支剪輯器的分數了。現在它們都在了，分數量得到東西了。

**這輪做完之後還欠著的，只有一條**：設計原則裡「每條 skill 指引都要有對應的 benchmark case」
（見下方）。它等 §11，而且知道在欠。

## 刻意不做的事

這些都評估過、有理由地不做，不是忘了。理由的細節在各章，這裡只列一行，
方便之後判斷「現在該做了嗎」——大部分的答案是「等 §11 的語料量出來再說」。

| 不做的 | 理由 | 見 |
|---|---|---|
| 逐鏡頭一個畫質分數 | 權重在合成素材上訂只會自己騙自己；手持晃動在 talking head 是失誤、在 vlog 是風格 | §1 |
| person detector | `faces: 0` 只代表沒看到臉；另一個模型、另一個數量級的成本，還沒有東西需要它 | §1 |
| `ClipKind.ACTION` | 「多動算有事情在發生」沒有語料訂不出來 | §1、§13 |
| 避開失焦的幀 | 「多糊算糊」要一個門檻；機制已留好位置 | §3 |
| B-roll 的「畫面弱」「剪點生硬」兩個訊號 | 前者要畫質門檻，後者沒有量測對應得上 | §4 |
| 自動偵測「不能蓋掉的關鍵動作」 | 要動作辨識，而且是判斷；由 plan 的 `hold_picture` 明說 | §4 |
| 轉場時自動柔化聲音 | 多長、哪一邊是判斷；手動的控制項本來就在 | §2、§6 |
| 用拍分辨旁白與音樂 | 旁白也是有聲無畫，會被量出假的拍；分辨它要看逐字稿覆蓋率，又是一個門檻 | §6 |
| 雙人的直式分割畫面 | 重構圖只跟最大的那張臉 | §9 |
| FCPXML 與 EDL 裡的轉場 | 各家解讀轉場不同（我們結束在剪點上，FCP 預設跨在剪點上），寫錯比不寫糟；OTIO 的表示法剛好對得上，所以只有 OTIO 帶 | §9 |
| 正式 render 用預覽快取 | 快取畫面是低畫質有損的 | §7 |
| 「開頭無聊」的 amendment | 解法是換選材或重排，那是判斷 | §8 |
| 工具呼叫次數、token、時間的成本指標 | 不是編譯結果的函式，要先決定由誰記錄 | §11 |

## 設計原則

新功能照這幾條做，它們約束的是還沒寫的東西：

- **判斷留給模型與使用者，計算留給伺服器。** 伺服器不替模型決定結構，
  也不把模型寫的東西當成既成事實。
- **要模型做判斷時，先用規則過量產生候選，模型只能在候選裡裁決，結果連同輸入雜湊釘住。**
  輸出空間有界，驗證就是成員資格檢查；模型判斷錯了，錯的也只是選擇，不會是算術。
- **驗證不過就退回並說明理由，不要默默修正。** 默默修正等於把判斷偷偷搬回伺服器。
- **本機優先。** 偵測與轉錄一律在本機。縮圖與逐字稿會隨工具結果離開本機這件事，
  要在 README 與 skill 裡講清楚，不要用「全部本機」這種含糊說法帶過。
- **不維持工具介面相容。** 這台 server 沒有外部使用者，介面該改就改，不留轉接層。
  資料層也一樣：儲存是 JSON、Pydantic 欄位都有預設值，加欄位天生相容；
  語意真的變了的地方（例如字幕改成綁語意片段）就讓舊資料重新產生一次，不寫遷移程式。
- **每條 skill 指引都要有對應的 benchmark case。** 沒有 case 能證明它有用的指引，不寫。
  這條是為了防止指南隨時間膨脹。
  **這條目前欠著。** §11 排在最後，所以在它做完之前沒有任何 case 可以對應，而 §2 到 §9
  每一章都往指南加了東西。§10 已經把指南拆成一檔一題、主檔縮到一半以下，
  但「逐條補 case、補不出來就刪」要等 §11 的語料才做得到。這是知道而且認了的債，不是忘了。
  在那之前，往指南加東西要能說出「哪一個工具呼叫少了它就會做錯」。

## 1. Analysis — 完成

§1 的量測做完了，細節寫在 `architecture.md`，這裡不重述。刻意沒做的是這幾件：

### 刻意沒做的：逐鏡頭一個品質分數

原本寫的是「曝光、清晰度、抖動程度，**逐鏡頭一個分數**……選材時先排除『拍壞的』，
不必讓模型看圖判斷」。實際做出來的是五個各自獨立的原始數字，**沒有合成那一個分數**。

理由：要合成一個分數就得決定曝光差一級、糊一點、晃一點各扣多少分，那組權重
在合成素材上訂出來只會是自己騙自己（同 §13）。而且「拍壞的」對 talking head
跟 vlog 本來就不是同一件事——手持晃動在前者是失誤，在後者是風格。
所以現在是伺服器給數字、模型下判斷，代價是「不必讓模型看圖判斷」只做到一半：
模型不用看圖，但還是得自己決定門檻。

等語料到位（§11）再決定要不要合成，以及是不是該按片型給不同的權重。

### 要另一個模型或語料才做得到的

- **人物偵測只做到臉。** 背對鏡頭的人偵測不到，所以 `faces: 0` 的意思是
  「沒看到臉」，不是「畫面裡沒人」。要真的回答後者得再加一個 person detector，
  那是另一個模型、另一個數量級的成本，等到有東西真的需要它再說。
- **`ClipKind.ACTION` 還是沒分出來。** 動態量到了，但「多動算有事情在發生」
  沒有語料訂不出來。等語料（見 §13）。

## 2. Timeline — 完成

四項都做完了，細節寫在 `architecture.md`。這裡只留下之後會影響別人的三件事。

**重疊是兩個明確的例外，不是放寬規則。** 同軌的畫面仍然不准重疊；
`audio_lead` / `audio_lag` 讓**聲音**伸出自己的畫面之外，`transition_in` 讓**畫面**
混進前一顆的尾巴——兩者都不移動任何 clip，剪點留在原地，多出來的媒體從
`source_range` 之外取。`validate_project` 因此只擋畫面重疊。

**轉場結束在剪點上，不跨過它。** 這是為了不動時間軸：轉場吃掉的是自己的前導，
所以成片長度不變、後面的東西不用重排。代價是它跟一般 NLE 的「以剪點為中心」不一樣，
真的要置中就得把兩邊都移動，那才是會動到時間軸的設計。

**聲音沒有跟著轉場。** 畫面轉了，聲音仍然是硬切——要柔化就給出場的 clip
`audio_fade_out`、進場的 `audio_fade_in`（或用 `audio_lead` / `audio_lag` 讓兩邊重疊）。
把兩者綁在一起是一個判斷（多長？兩邊都要嗎？），沒有語料之前不做；§6 查過一次，結論相同。

**dip 的前導只有一半。** dissolve 與 wipe 是一次混合，向後伸手拿整段長度的前導；
dip 是兩次混合中間夾一個顏色，只有第二次碰到進場的 clip，所以它只拿一半。
`Clip.run_up` 是唯一該問的地方——編譯器與驗證都從它算，別自己乘 `seconds`。

### 沒做的轉場

xfade 原生有 58 種，這裡只開三種（dissolve、wipe、dip），因為剩下的是同一個
機制換一個名字，而每多一種就多一條要驗證的算術。要加的時候加一個 kind 就好，
型別已經在那裡了——這正是 `Transition` 存在的理由。

## 3. Rough cut — 完成

這些清理不需要判斷力，所以由程式碼做，而不是寫在 skill 裡叫模型注意。
**剪點吸附**：每個 piece 都在實測 headroom 內加呼吸，而 `head` / `tail`
這兩個會落在任意秒數的 trim 會吸附到最近的詞邊界（`SNAP_SECONDS = 1.0` 以內，暫定值）。
在實際素材上，切在字中間的剪點 EP2 歸零、EP1 從 15 降到 1，成片長度只差半秒。
**底線表的「切到字 = 0」還沒達成**：EP1 剩下的那一個落在一個長 2.24 秒的詞裡，
前後乾淨落點各距 1.12 秒，超過願意移動的範圍——移得比要修的毛病還大就不值得，
所以留著並回報。要不要放寬那個門檻等語料再決定（見 §13）。
**句子沒講完就切掉**不自動修：實測補完 EP1 全部要 148 秒（片長的 39%）、
EP2 要 86 秒（22%），那是在改變成片長度，
所以由 `check_plan` 回報「總共還差幾秒、最長的是哪一段」，交給定長度的人決定。
編譯器動過的剪點也會回報——移動雖然是算術，仍然是改了別人的剪接。

四個清理階段（去氣口、去重拍、首尾修整、避開壞幀）已經做完，細節寫在
`architecture.md`。這裡只留下做的時候發現、之後還會咬人的兩件事：

**靜音偵測器與轉錄器對「安靜」的認定差很多。** 去氣口第一版直接在偵測到的靜音
邊緣切，在三支真實素材上把切到字的剪點從 0／1／0 變成 6／14／8——因為詞的結束時間
經常延伸進被判為安靜的那一段。現在每個新剪點都要先吸附到真的可以切的地方，
吸不到就整個氣口留著並回報。修正後三支的切到字剪點不變，死空氣各少了
2.6／8.6／5.4 秒。這個分歧不是 bug，是兩個量測本來就不同；之後任何依賴靜音的功能
（§6 的語音增強、節拍對齊）都要記得它。

**對焦跑掉的幀還沒避開。** 黑畫面與凍結畫面是偵測器直接給的布林區間，不需要門檻；
「多糊算糊」需要在 `shots.blur` 上訂一個數字，而那是 §13 拒絕在合成素材上訂的那一類。
機制留了位置（`CleanCuts.bad_picture` 是一份區間清單，多一個來源就是多接一個），
等語料到了補上去即可。

### 品質底線（可測）

這幾條要變成 benchmark 的自動指標，而不是指南裡的建議：

| 指標 | 目標 |
|---|---|
| 切到字的剪點 | 0 |
| 落在壞幀上的剪點 | 0 |
| 成片長度與目標的誤差 | < 10% |
| 必留段落覆蓋率 | > 90% |
| 必剔段落洩漏率 | 0 |

## 4. B-roll — 完成

`EditPlan.broll` 與編譯做完了，四條覆蓋規則全部在編譯器裡（違規就退回並說明理由），
`propose_broll` 產生候選位置，細節寫在 `architecture.md`。這裡只留下兩件事：

**原本列的三個訊號只做了一個。** roadmap 列的是「聲音好但畫面弱、同一顆鏡頭停太久、
剪點太生硬」，其中只有「同一顆鏡頭停太久」落地；另外補了一個原本不在清單上的
「連續幾個視窗維持同一個畫面」，因為同一個檔案往前走就是同一顆鏡頭沒動過，
是同一個問題換個樣子。
「畫面弱」需要在曝光與模糊上訂一個門檻，那是 §13 拒絕在合成素材上訂的那一類；
量測都在每個片段的 `scores` 上，要讀的人自己讀。「剪點太生硬」同理——沒有量測對應得上。

**「不蓋掉關鍵動作」是 plan 上的一個布林值，不是偵測出來的。** `Selection.hold_picture`。
要自動判斷「說話者正在指東西」需要動作辨識，那是另一個模型；而且判斷本來就該留給模型。
沒有人說，就是不知道。

## 5. Subtitles — 完成

字幕已經改成**綁素材時間**（哪個檔、該檔第幾秒），剪輯搬動時自己跟著走，
`SKILL.md` 那條「caption last」也跟著刪掉了。原訂的做法是綁 semantic clip 的
`from_clip_ids`，實作時改掉了，理由記在這裡免得之後有人以為是漏做：
語意時間軸一重建（重新分析素材、或動到 `DERIVATION_VERSION`），clip id 全部會變，
那正是這條要消滅的「全錯位」；而且 `from_clip_ids` 只有編譯過的 clip 才有，
手工用 `insert_clip` 建的專案根本沒有，會變成不能上字幕。
素材秒數兩種情況都不受影響。

樣式預設集、雙語、逐字動態字幕、講者標示四項都做完了，細節寫在 `architecture.md`。
2026-09-26 實際跑了十支之後補了一次：字幕改成**一次一行**（太長就依序換行而不是往上疊），
直式預設集的位置調低、字級調小——原本 `tiktok` 在 1080 寬一行只放得下九個字，
一句話疊三行、字幕塊頂到畫面六成高。
這裡只留下兩件之後會咬人的事：

**預設集裡的數字是平台慣例，不是量出來的。** 安全區是各家 app 自己的按鈕與字卡蓋掉多少
畫面，字級是手機拿在手上看得清楚要多大。這些會隨 app 改版而變，所以全部收在
`CAPTION_PRESETS` 一個地方，改一次就到處生效。它們跟 §13 那些「等語料」的門檻不同類——
語料量不出 TikTok 的按鈕在哪裡。

**跨檔案講者**：字幕的講者標籤跟它所在的片段一樣是跨檔案接起來的
`V1`／`V2`，`speaker_names` 對的也是這一組。接的範圍跟片段一致——plan 編譯出來的剪輯
用那份 plan 的語意時間軸的所有檔案，手工拼的剪輯用正在上字幕的檔案——否則同一個人
可能在字幕上和片段上被編成不同的號碼。在嵌入向量被留下來之前分析的檔案，字幕上仍是
它自己的 `S1`／`S2`；skill 寫明要重新分析而不是替它對名字。

## 6. Audio — 完成

語音增強、逐講者響度一致、節拍對齊、分段換曲都做完了，細節寫在 `architecture.md`。
2026-09-26 實際跑了十支之後補了一次：另錄的旁白會自動被拉到標準音量，相機原音與配樂在它
講話時讓開——第一支片子街聲比旁白大十分貝。下面那段「要分辨音樂還是講話得看逐字稿蓋了多少」
就是這次用的判準（`VOICE_SPEECH_SHARE`），門檻先訂 0.5。
這裡只留下之後會咬人的事：

**節拍是分析時量的，而且只量配樂。** 有聲音沒畫面的檔案才跑節拍偵測——對人講話跑，
會在音節裡找到一個拍。所以一支 MV 當配樂用時不會有節拍；真的需要再說。
反過來，單獨錄的旁白也是有聲音沒畫面，它一樣會被量出一個拍，而且是假的
（工作區那支開場配音量出 135.7 BPM，對比 6.27，高過三首真的配樂）。
`MIN_CONTRAST` 擋不住它，因為講話的音節本來就是很強的 onset。
目前無害——拍只有在那個檔案被當成配樂 cue 且開了 `cut_on_beat` 時才被讀——
但要分辨「這是音樂還是講話」得看逐字稿蓋了多少，那又是一個門檻，等語料。
同一次也在三首真的配樂上跑過（lofi 74.9、木吉他 105.4、鋼琴 126.1 BPM），
拍與拍的間隔標準差 5–21ms，一首五分鐘的歌不到一秒。速度對不對沒有人工標註可以比，
這要等 §11。
沒有穩定脈動的音樂（環境音、長音 pad）回答「沒有拍」，這是答案不是失敗，
要求對拍的 plan 會被退回並說明。

**對拍只准在靜音裡移動剪點，這是刻意的。** 比「移出詞中間」嚴得多：不得吃掉最後一個詞
後面那口呼吸、不得碰到下一個詞的呼吸、不得超過 `BEAT_SNAP_SECONDS`。所以講話很密的
素材上大部分剪點會對不上拍，而且會照實回報。要讓它對得更多，是去改選材
（留更多空氣），不是放寬這條——放寬就是讓配樂決定句子能不能講完。
沒有逐字稿的素材一律不動，因為沒有人知道那裡有沒有字。

**換曲預設頭尾相接，要交叉淡化得明說。** `MusicPlan.crossfade_seconds` 大於 0 時，
進場的歌提早那麼多秒、放在第二條音樂軌（`music_b`）上，兩首交錯；它也從自己的進入點
往回多播同樣長度，所以到了剪點正好在 cue 說的那一秒——對拍的 cue 仍然在拍上。
重疊多長是品味，所以只照 plan 寫的做，不替人決定；比出場那段還長就退回。

**B-roll 的切入點不對拍。** 它綁在句子邊界上，那一條比拍重要。

**溶接時的聲音查過了，結論是不做。** 原本寫的是「要自動柔化得先決定多長、哪一邊」，
而那兩個問題現在仍然沒有語料可以回答。要手動柔化的控制項**本來就在**——
出場的 clip 給 `audio_fade_out`、進場的給 `audio_fade_in`，兩者跟 `transition_in`
各自獨立。所以這一項缺的不是機制，是那個判斷，而判斷照原則本來就不該由伺服器做。
skill 裡已經寫明要問使用者。

配樂該低多少才對是品味，沒有訂。

## 9. Render — 完成

多平台（跟臉重構圖）、章節與封面、EDL／OTIO／FCPXML 匯出、render 前檢查都做完了，
細節寫在 `architecture.md`。這裡只留下之後會咬人的事：

**臉移出去時選了切，不選推。** 理由寫在 `reframe.py` 開頭：推是沒人拍過的運鏡，
而且由一秒兩次的偵測驅動會追不上或抖。這是一個方向選擇，不是等語料的門檻；
但「靠邊多久才切」「兩次剪接至少隔多久」是門檻，列在 §13。
只看最大的那張臉，所以兩個人一左一右的對談在直式裡只會跟其中一個——
要兩個都留住得做分割畫面，那是另一件事。

**一次一種比例。** `render_project` 的 `frame` 一次一個，三種比例叫三次（記憶體閘門會排隊）。
沒做成一次回三個 job，因為那會改掉工具的回傳形狀，換來的只是少兩次呼叫。

**檢查會擋 render，但只擋有證據的事。** 沒分析過的檔案什麼都不會被找到，這不代表它沒問題。
爆音的判準（峰值貼頂且被削平）是暫定值；黑畫面沿用分析時的偵測門檻；
凍結畫面可能包含刻意的靜止鏡頭，所以訊息寫的是事實，放行權在使用者。

**匯出帶變速，轉場只有 OTIO 帶。** 變速三種格式都帶（EDL 的 M2 行、OTIO 的
`LinearTimeWarp`、FCPXML 的 `timeMap`），每段在時間軸上的長度也改用播放長度——
之前用的是來源長度，所以有變速的 clip 之後每一段的位置其實都算錯了。
轉場只有 OTIO 帶：它的 `in_offset` 剛好表達得出「結束在剪點上」；FCPXML 與 EDL 的轉場
各家解讀不同，寫錯比不寫糟，照實列在 `left_behind`。FCPXML 另外帶每段的音量。
來源檔自帶的 timecode 在匯出時讀（專業攝影機的檔案常從 10:00:00:00 起算，drop-frame 也照規則算），
EDL、OTIO、FCPXML 都照它對位。EDL 與 OTIO 用 OpenTimelineIO 的轉接器讀回驗證過；
FCPXML 的 `timeMap` 是照 Apple 的格式定義寫的，轉接器只驗得到時間軸位置，
沒有 Final Cut 可以實測倍速對應。

`test_skill_resources.py` 的雙向比對擴充了：工具與操作照舊；**不存在的 action**

那要等 §11 的語料庫與 L3 評測才做得到；在那之前，指引是否真的讓剪輯變好只是推測。
原本的問題陳述留在下面，作為為什麼要拆的紀錄：

`clip-editing/SKILL.md` 是一份**知識傾倒**，不是一份**決策程序**：工具說明、概念、

### 改版原則

1. **能寫成程式碼的就不要寫在 skill 裡。** 沒有判斷空間的規則屬於 compiler，不屬於指南。
2. **漸進式揭露。** 主檔只回答「現在該做什麼」，其餘按觸發條件載入。
   每個子檔要有明確的「什麼時候讀我」。
3. **一個檔回答一個問題。** 不要有「雜項」。
4. **每條指引都要有對應的 benchmark case。**

之後新增指引照這四條；第四條就是上面欠著的那一條。

## 11. Benchmark — 評測

**這是下一個工作項目。** §1 到 §10 已經做完，評測要量的東西都在了。

### 從哪裡開始

順序照相依性，每一步都能單獨交付：

1. **把三份草稿案例變成真的案例**（`corpus/README.md` 列了待辦）：must_keep 砍到非留不可、
   補 must_drop 與 cut_windows、換回當時真的講的指令。做完才算得出第一個 L2 分數。
2. **基準分數**：用現在的 planner 跑那三支，把分數存下來。之後的每一次改動都跟它比。
3. **語料的語意時間軸存成 fixture**，連 `candidate_hash` 一起釘住（見「迴歸」）。
4. **擴充語料到 50 支**，照「語料庫」的維度鋪開。這一步最慢，但 §13 的數字要它才調得動。
5. **L3 的判官**：先做校準集，再談分數（見「L3 的評測 AI」）。
6. 有了語料之後回頭做兩件欠著的事：§13 的門檻逐一調校，以及每條 skill 指引補 case。

### 三層

| 層 | 測什麼 | 怎麼測 | 現況 |
|---|---|---|---|
| L1 工具正確性 | 操作有沒有算錯、render 出來對不對 | 現有 pytest | ✅ 已有 |
| L2 規劃品質 | 選材與結構好不好 | 對 plan 自動評分，不必 render | 🟡 計分器已有，語料還是草稿 |
| L3 成片品質 | 剪得好不好 | 評測 AI 依 rubric 評分 | ⬜ 要做 |

L2 是重點：它跑得快、可以每次 commit 都跑，而且因為 plan 是結構化的，
大部分指標可以自動算。

### 語料庫

目標 50–100 支影片，維度要鋪開，不能全是同一種素材：

| 維度 | 要涵蓋 |
|---|---|
| 類型 | talking head、vlog、教學、活動紀錄、產品開箱、多人對談 |
| 長度 | 30 秒到 60 分鐘都要有 |
| 語言 | 中文（台灣國語為主）、英文、中英混雜 |
| 聲音 | 乾淨收音、環境吵雜、無人聲、只有音樂 |
| 畫面 | 直式與橫式、手持與固定、光線好與壞 |
| 品質 | 刻意包含拍壞的素材（失焦、黑畫面、誤錄） |

### 每支影片配的東西

素材本身不是題目，**素材 + 指令 + 參考標註**才是：

- 一到三句使用者指令（從明確到含糊都要有，含糊的才測得出判斷力）
- 標註：必須保留的區段、必須剔除的區段、可接受的剪點範圍
- rubric：這支影片剪成什麼樣算好，分項給分
- 不是唯一解。好的剪法不只一種，所以評的是「有沒有踩到地雷」與「有沒有抓到重點」，
  不是「跟標準答案有多像」

### 自動指標

`app/benchmark/metrics.py` 已經算得出前四項，全是編譯後 windows 與分析結果的純函式：

- 必留段落覆蓋率 / 必剔段落洩漏率 ✅（依秒數加權，不是依段數）
- 成片長度與目標的誤差 ✅
- 切到字的剪點數、落在壞幀上的剪點數 ✅
- 剪點與最近安全邊界的距離分佈 ✅（每個剪點的餘裕，另給最小值與中位數）
- 落在標註「可接受剪點範圍」外的剪點數 ✅（沒畫範圍的檔案不算它違規，那是語料的缺口不是計畫的錯）
- 成本：工具呼叫次數、token 用量、wall-clock 時間 ⬜
  計分器裡**沒有**它們的欄位。這三項不是編譯結果的函式，是跑模型那一端才量得到的東西，
  要做就得先決定由誰記錄；在那之前不放空欄位假裝留了位置。

還沒做的另外兩件，都在 §11「迴歸」底下：語料的語意時間軸存成 fixture 並釘住
`candidate_hash`，以及用 P_k / WindowDiff 另外評切分。後者 roadmap 本來就說「切分本身另外評」，
所以不混進 L2 的數字裡。

剩下最大的缺口仍然是**語料**，但起點有了：三支成片已經變成 `corpus/` 底下的三份案例
（`0902-closing`、`taipei-internship`、`tainan-trip`），細節與待辦寫在 `corpus/README.md`。
**三支都是 `annotated_by: draft`，所以現在一分都算不出來**——草稿把成片用過的每一段
都標成必留，must_keep 的總長幾乎等於目標長度，那不是底線是標準答案。
要做的是把它砍到只剩非留不可的，補上 must_drop 與 cut_windows，
並把兩支反推的 instruction 換成當時真的講的話。

原本以為這三支「有被排除的理由」可以拿來當必剔——**沒有**，三份 plan 的 `rejected`
都是空的。`0902-closing` 的指令裡雖然點名了一段不要用，
但那段素材已經不在資料夾裡，所以連它也標不了。

一份案例配一句指令，不是一份案例配三句。roadmap 說「一到三句使用者指令」，
但不同指令對應的必留／必剔本來就不一樣——同一批素材配三句就是三題，
共用欄位只會讓標註彼此漂移。

**成片跟素材放在同一個資料夾。** `raw/<日期>/<日期>.mp4` 全部是成片（30fps、匯入過、
不在任何語意時間軸裡）。組 `footage` 時不能用列資料夾的方式，否則等於把答案交出去。

### L3 的評測 AI

判官本身是一個會漂移的量測儀器，不先處理下面四件事，分數會看起來很科學、
實際上量不到東西：

- **先校準。** 挑 10 支左右自己評一次，跟判官比對。兩邊對不起來的話，
  要改的通常是 rubric 不是判官——多半是 rubric 寫得太抽象。
  沒做這一步，你不會知道判官在量「剪得好不好」還是在量「像不像它自己會剪的」。
- **釘住判官版本。** 每一筆分數都記下判官的模型與 prompt 版本。
  換了模型還拿舊分數比，等於換了尺再說東西變長了。
- **逐項給分，要求附證據。** 不要整體 1–10 分，而是 rubric 每項各自判定，
  並要求指出時間點當證據。有證據的分數才查得動，
  也才擋得住判官編一段聽起來很合理的評語。
- **迴歸用兩兩比較，不用絕對分數。** 判官給絕對分數不穩，
  但比較「A 和 B 哪個好」相當可靠。而迴歸要問的本來就是
  「這次改動有沒有變好」，正好是比較題。

### 迴歸

每次改 skill、planner 或分析參數就跑一次，留下分數。
分數退步就是 regression，跟測試失敗同等對待。

**語意時間軸要當成固定裝置。** 語料庫的語意時間軸建一次就存進 fixture，
評 planner 時不重建。`build_semantic_timeline` 對不變的輸入會回傳同一份建置，
所以這件事現在做得到——但要記得同一份 fixture 也要釘住 `candidate_hash`，
否則調了候選權重會連帶動到段落。

**切分本身另外評。** 人工標好一批段落邊界當答案，用 P_k 與 WindowDiff
這類文字切分的標準指標評段落切分。改切分演算法時看這組分數，
改 planner 時看 L2——兩者不要混在同一個數字裡。

## 13. 等語料才能決定的事

方向都定了，剩下的是量的問題——沒有真實素材就只是在猜數字。這些全部等 §11 的語料到位再定，
而且每調一個都要重跑 §11，看分數是變好還是只是變了。

程式裡每一個暫定值都是一個有名字的常數，註解寫明「Provisional」；下面三張表就是它們的全部。
新增暫定值時兩邊一起加，不偷偷塞魔術數字。

### 還沒有常數、但同樣要語料回答的

- **畫質與音訊的門檻**：多糊算糊、多暗算暗、多晃算晃、底噪多高該降噪，
  以及 `ClipKind.ACTION` 從多少動態開始算。數字都量得到了，但門檻在合成素材上訂只會自己騙自己。
  這些一旦訂下來，§1 的逐鏡頭畫質分數、§3 的避開失焦、§4 的「畫面弱」才做得了。
- **`section` 的長度上下限**：目前刻意不強制，連警告都不給。
- **判官與人的一致度要多高才算可用**：校準集對不到什麼程度就得重寫 rubric。
- **L2 各項指標的權重**：切到字和長度超標都扣分，但不該扣一樣多。
- **語料庫的維度配比**：§11 的維度表列了要涵蓋什麼，沒說各佔幾支。
  等看到手上實際有哪些素材再配。

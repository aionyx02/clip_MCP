# Roadmap — clip-mcp 2.0

**這份文件只留還沒做的事。** 已經落地的東西寫在 `architecture.md`，不在這裡重述。

2.0 的核心想法——把剪輯決策變成被持久化的資料——骨架已經完成：語意時間軸、
段落與主題、剪輯計畫與編譯器、出身與鎖定、素材的量測（畫面、聲音、人臉、說話者），
以及時間軸的基本盤（J/L cut、溶接、變速、段落標記）。
剩下的是兩類：**還沒有的剪輯功能**（B-roll、字幕樣式、聲音處理、輸出擴充），
以及**還沒有辦法證明剪得好不好**。

後者是瓶頸。沒有可重複的評分，skill 與 planner 的每一次調整都只能憑感覺，
而剪輯品質的感覺特別不可靠。**但它排在最後**：先把 §2 到 §10 的功能做齊，
再回頭用真實素材驗品質。理由是評測要量的東西得先存在——現在量出來的分數，
幾個月後功能長齊時已經不是同一支剪輯器的分數了。

---

## 設計原則

新功能照這幾條做，它們約束的是還沒寫的東西：

- **判斷留給模型與使用者，計算留給伺服器。** 伺服器不替模型決定結構，
  也不把模型寫的東西當成既成事實。
- **要模型做判斷時，先用規則過量產生候選，模型只能在候選裡裁決，結果連同輸入雜湊釘住。**
  輸出空間有界，驗證就是成員資格檢查；模型判斷錯了，錯的也只是選擇，不會是算術。
- **驗證不過就退回並說明理由，不要默默修正。** 默默修正等於把判斷偷偷搬回伺服器。
- **本機優先。** 偵測與轉錄一律在本機。縮圖與逐字稿會隨工具結果離開本機這件事，
  要在 README 與 skill 裡講清楚，不要用「全部本機」這種含糊說法帶過。
- **不維持工具介面相容。** 這台 server 沒有外部使用者，介面該改就改，不留轉接層。
  資料層也一樣：儲存是 JSON、Pydantic 欄位都有預設值，加欄位天生相容；
  語意真的變了的地方（例如字幕改成綁語意片段）就讓舊資料重新產生一次，不寫遷移程式。
- **每條 skill 指引都要有對應的 benchmark case。** 沒有 case 能證明它有用的指引，不寫。
  這條是為了防止指南隨時間膨脹。

## 1. Analysis — 完成，除了一項

§1 的量測做完了，細節寫在 `architecture.md`，這裡不重述。剩下這些：

### 刻意沒做的：逐鏡頭一個品質分數

原本寫的是「曝光、清晰度、抖動程度，**逐鏡頭一個分數**……選材時先排除『拍壞的』，
不必讓模型看圖判斷」。實際做出來的是五個各自獨立的原始數字，**沒有合成那一個分數**。

理由：要合成一個分數就得決定曝光差一級、糊一點、晃一點各扣多少分，那組權重
在合成素材上訂出來只會是自己騙自己（同 §13）。而且「拍壞的」對 talking head
跟 vlog 本來就不是同一件事——手持晃動在前者是失誤，在後者是風格。
所以現在是伺服器給數字、模型下判斷，代價是「不必讓模型看圖判斷」只做到一半：
模型不用看圖，但還是得自己決定門檻。

等語料到位（§11）再決定要不要合成，以及是不是該按片型給不同的權重。

### 要模型才拿得到、但還沒做的

- **人物偵測只做到臉。** 背對鏡頭的人偵測不到，所以 `faces: 0` 的意思是
  「沒看到臉」，不是「畫面裡沒人」。要真的回答後者得再加一個 person detector，
  那是另一個模型、另一個數量級的成本，等到有東西真的需要它再說。
- **說話者標籤跨檔案不通。** 同一個人在兩支檔案裡會是不同標籤。
  要串起來得比對嵌入向量，而嵌入目前沒有被留下來。§5 的講者標示如果要跨檔案，
  這件事得先做。
- **`ClipKind.ACTION` 還是沒分出來。** 動態量到了，但「多動算有事情在發生」
  沒有語料訂不出來。等語料（見 §13）。

## 2. Timeline — 完成

四項都做完了，細節寫在 `architecture.md`。這裡只留下之後會影響別人的三件事。

**重疊是兩個明確的例外，不是放寬規則。** 同軌的畫面仍然不准重疊；
`audio_lead` / `audio_lag` 讓**聲音**伸出自己的畫面之外，`transition_in` 讓**畫面**
混進前一顆的尾巴——兩者都不移動任何 clip，剪點留在原地，多出來的媒體從
`source_range` 之外取。`validate_project` 因此只擋畫面重疊。

**轉場結束在剪點上，不跨過它。** 這是為了不動時間軸：轉場吃掉的是自己的前導，
所以成片長度不變、後面的東西不用重排。代價是它跟一般 NLE 的「以剪點為中心」不一樣，
真的要置中就得把兩邊都移動，那才是會動到時間軸的設計。

**聲音沒有跟著轉場。** 畫面轉了，聲音仍然是硬切——要柔化得自己加
`audio_lead` / `audio_lag`。把兩者綁在一起是一個判斷（多長？兩邊都要嗎？），
沒有語料之前不做。

**dip 的前導只有一半。** dissolve 與 wipe 是一次混合，向後伸手拿整段長度的前導；
dip 是兩次混合中間夾一個顏色，只有第二次碰到進場的 clip，所以它只拿一半。
`Clip.run_up` 是唯一該問的地方——編譯器與驗證都從它算，別自己乘 `seconds`。

### 沒做的轉場

xfade 原生有 58 種，這裡只開三種（dissolve、wipe、dip），因為剩下的是同一個
機制換一個名字，而每多一種就多一條要驗證的算術。要加的時候加一個 kind 就好，
型別已經在那裡了——這正是 `Transition` 存在的理由。

## 3. Rough cut — 機械性清理

這些清理不需要判斷力，所以應該由程式碼做，而不是寫在 skill 裡叫模型注意。
**剪點吸附**做了大半：每個 piece 都在實測 headroom 內加呼吸，而 `head` / `tail`
這兩個會落在任意秒數的 trim 會吸附到最近的詞邊界（`SNAP_SECONDS = 1.0` 以內，暫定值）。
在實際素材上，切在字中間的剪點 EP2 歸零、EP1 從 15 降到 1，成片長度只差半秒。
**底線表的「切到字 = 0」還沒達成**：EP1 剩下的那一個落在一個長 2.24 秒的詞裡，
前後乾淨落點各距 1.12 秒，超過願意移動的範圍——移得比要修的毛病還大就不值得，
所以留著並回報。要不要放寬那個門檻等語料再決定（見 §13）。
**句子沒講完就切掉**不自動修：實測補完 EP1 全部要 148 秒（片長的 39%）、
EP2 要 86 秒（22%），那是在改變成片長度，
所以由 `check_plan` 回報「總共還差幾秒、最長的是哪一段」，交給定長度的人決定。
編譯器動過的剪點也會回報——移動雖然是算術，仍然是改了別人的剪接。

四個清理階段（去氣口、去重拍、首尾修整、避開壞幀）已經做完，細節寫在
`architecture.md`。這裡只留下做的時候發現、之後還會咬人的兩件事：

**靜音偵測器與轉錄器對「安靜」的認定差很多。** 去氣口第一版直接在偵測到的靜音
邊緣切，在三支真實素材上把切到字的剪點從 0／1／0 變成 6／14／8——因為詞的結束時間
經常延伸進被判為安靜的那一段。現在每個新剪點都要先吸附到真的可以切的地方，
吸不到就整個氣口留著並回報。修正後三支的切到字剪點不變，死空氣各少了
2.6／8.6／5.4 秒。這個分歧不是 bug，是兩個量測本來就不同；之後任何依賴靜音的功能
（§6 的語音增強、節拍對齊）都要記得它。

**對焦跑掉的幀還沒避開。** 黑畫面與凍結畫面是偵測器直接給的布林區間，不需要門檻；
「多糊算糊」需要在 `shots.blur` 上訂一個數字，而那是 §13 拒絕在合成素材上訂的那一類。
機制留了位置（`CleanCuts.bad_picture` 是一份區間清單，多一個來源就是多接一個），
等語料到了補上去即可。

### 品質底線（可測）

這幾條要變成 benchmark 的自動指標，而不是指南裡的建議：

| 指標 | 目標 |
|---|---|
| 切到字的剪點 | 0 |
| 落在壞幀上的剪點 | 0 |
| 成片長度與目標的誤差 | < 10% |
| 必留段落覆蓋率 | > 90% |
| 必剔段落洩漏率 | 0 |

## 4. B-roll — 補充畫面

粗剪完成後的第二遍，不是同時做。

1. 在粗剪上找需要蓋畫面的位置：聲音好但畫面弱、同一顆鏡頭停太久、剪點太生硬。
2. 從語意時間軸用標籤與文字檢索語意相關的畫面（`query_clips` 的 `tag` 與 `text` 已經可用）。
3. 蓋到上層 video track，`volume: 0`，底下的聲音繼續跑。

第 3 步的機制已經有了（上層軌道 + 不給 `layout` 就滿版），缺的是前兩步的判斷依據，
以及 `EditPlan` 裡對應的 `broll` 欄位與編譯——目前 plan 只編譯主序列與音樂。

### 覆蓋規則

- 不蓋掉說話者正在做的關鍵動作（指東西、展示物品）
- 單段 B-roll 有最短與最長長度，太短像閃爍，太長會讓人忘記主線
- 一段話裡的 B-roll 密度上限
- 蓋的時機對齊句子邊界，不要在句中切進切出

## 5. Subtitles — 字幕

字幕已經改成**綁素材時間**（哪個檔、該檔第幾秒），剪輯搬動時自己跟著走，
`SKILL.md` 那條「caption last」也跟著刪掉了。原訂的做法是綁 semantic clip 的
`from_clip_ids`，實作時改掉了，理由記在這裡免得之後有人以為是漏做：
語意時間軸一重建（重新分析素材、或動到 `DERIVATION_VERSION`），clip id 全部會變，
那正是這條要消滅的「全錯位」；而且 `from_clip_ids` 只有編譯過的 clip 才有，
手工用 `insert_clip` 建的專案根本沒有，會變成不能上字幕。
素材秒數兩種情況都不受影響。

- **樣式預設集**：平台（YouTube / Reels / TikTok）各自的安全區、字級、描邊、位置。
- **雙語 / 逐字動態字幕**：短影音的標配。
- **講者標示**：多人對談時自動帶上名字或換色。§1 的說話者切分已經把 `S1`／`S2`
  填到語意片段上，缺的是把標籤帶進字幕，以及讓使用者把標籤換成真名。
  跨檔案要串成同一個人還做不到（見 §1）。

---

## 6. Audio — 聲音

- **節拍對齊**：把視覺剪點對到音樂的節拍上。快節奏短影音的成敗幾乎全在這裡。
- **分段換曲**：跟著 timeline markers 換曲或換段落（需要 §2 的 markers）。
- **語音增強**：降噪、去嘶聲、高通；手機錄的素材尤其需要。
- **逐講者響度一致**：兩個人音量差很多時，各自給不同的 gain，而不是靠整體正規化擺平。
  §1 的說話者段落與逐秒響度都有了，缺的是把每個人的 gain 算出來並套進編譯器。
- **溶接時的聲音**：畫面溶了聲音還是硬切（見 §2）。要自動柔化得先決定多長、哪一邊。

## 7. Preview — 預覽

- **增量預覽**：只重算改動到的片段，其餘走快取。目前改一個剪點就要整支重跑。
- **差異呈現**：這次改了什麼——哪幾段換掉、長度差多少——用文字或圖示表達，
  而不是讓使用者自己比對兩張 storyboard。`diff_plan` 已經能比較兩份 plan，
  缺的是把它對應到畫面上。
- **帶聲音的預覽**：storyboard 看得到節奏卻聽不到，音樂對齊與 ducking 沒辦法只靠眼睛確認。

## 8. User feedback — 回饋迴圈

原則與機制已經在：回饋改的是 plan 不是 timeline，手改過的 clip 會被釘住，
重新編譯不會洗掉。還缺的是把它變好用：

- 常見回饋語句到 plan 修改的對應表（太長 / 太趕 / 這段不要 / 開頭無聊 / 音樂太大聲…）
- 每次修訂留下版本，可以回退。目前 plan 有樂觀鎖的 `version`，但沒有留歷史，
  只能靠另存一份新 plan 來保留舊的。
- 一次回饋可能影響多處（「整體節奏太慢」不是改一段），要能表達全域性的調整

---

## 9. Render — 輸出

- **一次多平台**：同一份 plan 輸出橫式 / 直式 / 方形，直式靠追臉重構圖而不是硬裁中間。
  §1 的逐秒人臉位置已經有了（`get_analysis` 的 `faces` 會給該區間臉的中心與移動範圍），
  缺的是把它變成隨時間變的 crop，以及臉移出去時要用切的還是用推的。
- **章節與縮圖**：YouTube 章節、封面候選幀。章節可以從 plan 的 `beats` 直接長出來。
- **匯出給專業軟體**：EDL / OTIO / FCPXML。使用者想接手細修時，不該從零開始。
- **輸出前檢查**：黑幀、爆音、字幕出界、長度不符，在 render 前擋下來而不是之後才發現。

## 10. Skills 改版

`clip-editing/SKILL.md` 是一份**知識傾倒**，不是一份**決策程序**：工具說明、概念、
工作流程、對話語氣、操作對照表、預設值、錯誤處理全部塞在一起，每次整份載入。
細節寫得越多，模型越難分辨哪幾句話是這次該用的。而且它還在長。

### 改版原則

1. **能寫成程式碼的就不要寫在 skill 裡。** 沒有判斷空間的規則屬於 compiler，不屬於指南。
2. **漸進式揭露。** 主檔只回答「現在該做什麼」，其餘按觸發條件載入。
   每個子檔要有明確的「什麼時候讀我」。
3. **一個檔回答一個問題。** 不要有「雜項」。
4. **每條指引都要有對應的 benchmark case。**

### 規劃中的分工

| Skill | 回答的問題 | 何時載入 |
|---|---|---|
| `clip-editing` | 這句話對應哪個工具呼叫 | 每次 |
| `editing-intelligence` | 選哪些段落、怎麼排、多長 | 需要做剪輯判斷時 |
| `pacing-and-structure` | 節奏與結構（現有，保留並擴充） | 決定長度或結構時 |
| `platform-conventions` | 各平台的規格與慣例 | 指定平台時 |
| `feedback-handling` | 使用者的抱怨對應到 plan 的哪個修改 | 收到回饋時 |

現有的 `test_skill_resources.py` 雙向比對機制（工具與操作不得漂移）要保留，
並擴充到新的 skill 檔案。

## 11. Benchmark — 評測

**這是最後一個工作項目**，等 §2 到 §10 做完再開始。

### 三層

| 層 | 測什麼 | 怎麼測 | 現況 |
|---|---|---|---|
| L1 工具正確性 | 操作有沒有算錯、render 出來對不對 | 現有 pytest | ✅ 已有 |
| L2 規劃品質 | 選材與結構好不好 | 對 plan 自動評分，不必 render | 🟡 計分器已有，語料還是草稿 |
| L3 成片品質 | 剪得好不好 | 評測 AI 依 rubric 評分 | ⬜ 要做 |

L2 是重點：它跑得快、可以每次 commit 都跑，而且因為 plan 是結構化的，
大部分指標可以自動算。

### 語料庫

目標 50–100 支影片，維度要鋪開，不能全是同一種素材：

| 維度 | 要涵蓋 |
|---|---|
| 類型 | talking head、vlog、教學、活動紀錄、產品開箱、多人對談 |
| 長度 | 30 秒到 60 分鐘都要有 |
| 語言 | 中文（台灣國語為主）、英文、中英混雜 |
| 聲音 | 乾淨收音、環境吵雜、無人聲、只有音樂 |
| 畫面 | 直式與橫式、手持與固定、光線好與壞 |
| 品質 | 刻意包含拍壞的素材（失焦、黑畫面、誤錄） |

### 每支影片配的東西

素材本身不是題目，**素材 + 指令 + 參考標註**才是：

- 一到三句使用者指令（從明確到含糊都要有，含糊的才測得出判斷力）
- 標註：必須保留的區段、必須剔除的區段、可接受的剪點範圍
- rubric：這支影片剪成什麼樣算好，分項給分
- 不是唯一解。好的剪法不只一種，所以評的是「有沒有踩到地雷」與「有沒有抓到重點」，
  不是「跟標準答案有多像」

### 自動指標

`app/benchmark/metrics.py` 已經算得出前四項，全是編譯後 windows 與分析結果的純函式：

- 必留段落覆蓋率 / 必剔段落洩漏率 ✅（依秒數加權，不是依段數）
- 成片長度與目標的誤差 ✅
- 切到字的剪點數、落在壞幀上的剪點數 ✅
- 剪點與最近安全邊界的距離分佈 ✅（每個剪點的餘裕，另給最小值與中位數）
- 落在標註「可接受剪點範圍」外的剪點數 ✅（沒畫範圍的檔案不算它違規，那是語料的缺口不是計畫的錯）
- 成本：工具呼叫次數、token 用量、wall-clock 時間 ⬜
  計分器裡**沒有**它們的欄位。這三項不是編譯結果的函式，是跑模型那一端才量得到的東西，
  要做就得先決定由誰記錄；在那之前不放空欄位假裝留了位置。

還沒做的另外兩件，都在 §11「迴歸」底下：語料的語意時間軸存成 fixture 並釘住
`candidate_hash`，以及用 P_k / WindowDiff 另外評切分。後者 roadmap 本來就說「切分本身另外評」，
所以不混進 L2 的數字裡。

剩下最大的缺口仍然是**語料**，但起點有了：三支成片已經變成 `corpus/` 底下的三份案例
（`0902-closing`、`taipei-internship`、`tainan-trip`），細節與待辦寫在 `corpus/README.md`。
**三支都是 `annotated_by: draft`，所以現在一分都算不出來**——草稿把成片用過的每一段
都標成必留，must_keep 的總長幾乎等於目標長度，那不是底線是標準答案。
要做的是把它砍到只剩非留不可的，補上 must_drop 與 cut_windows，
並把兩支反推的 instruction 換成當時真的講的話。

原本以為這三支「有被排除的理由」可以拿來當必剔——**沒有**，三份 plan 的 `rejected`
都是空的。`0902-closing` 的指令裡雖然點名了一段不要用，
但那段素材已經不在資料夾裡，所以連它也標不了。

一份案例配一句指令，不是一份案例配三句。roadmap 說「一到三句使用者指令」，
但不同指令對應的必留／必剔本來就不一樣——同一批素材配三句就是三題，
共用欄位只會讓標註彼此漂移。

**成片跟素材放在同一個資料夾。** `raw/<日期>/<日期>.mp4` 全部是成片（30fps、匯入過、
不在任何語意時間軸裡）。組 `footage` 時不能用列資料夾的方式，否則等於把答案交出去。

### L3 的評測 AI

判官本身是一個會漂移的量測儀器，不先處理下面四件事，分數會看起來很科學、
實際上量不到東西：

- **先校準。** 挑 10 支左右自己評一次，跟判官比對。兩邊對不起來的話，
  要改的通常是 rubric 不是判官——多半是 rubric 寫得太抽象。
  沒做這一步，你不會知道判官在量「剪得好不好」還是在量「像不像它自己會剪的」。
- **釘住判官版本。** 每一筆分數都記下判官的模型與 prompt 版本。
  換了模型還拿舊分數比，等於換了尺再說東西變長了。
- **逐項給分，要求附證據。** 不要整體 1–10 分，而是 rubric 每項各自判定，
  並要求指出時間點當證據。有證據的分數才查得動，
  也才擋得住判官編一段聽起來很合理的評語。
- **迴歸用兩兩比較，不用絕對分數。** 判官給絕對分數不穩，
  但比較「A 和 B 哪個好」相當可靠。而迴歸要問的本來就是
  「這次改動有沒有變好」，正好是比較題。

### 迴歸

每次改 skill、planner 或分析參數就跑一次，留下分數。
分數退步就是 regression，跟測試失敗同等對待。

**語意時間軸要當成固定裝置。** 語料庫的語意時間軸建一次就存進 fixture，
評 planner 時不重建。`build_semantic_timeline` 對不變的輸入會回傳同一份建置，
所以這件事現在做得到——但要記得同一份 fixture 也要釘住 `candidate_hash`，
否則調了候選權重會連帶動到段落。

**切分本身另外評。** 人工標好一批段落邊界當答案，用 P_k 與 WindowDiff
這類文字切分的標準指標評段落切分。改切分演算法時看這組分數，
改 planner 時看 L2——兩者不要混在同一個數字裡。

## 12. 里程碑

| 階段 | 內容 | 完成標準 |
|---|---|---|
| **M1** | Benchmark 骨架與語料庫（50–100 支） | L1 接上 CI ✅；L2 計分器 ✅；語料庫 3/50 且全是草稿 🟡；基準分數 ⬜ |
| **M3′** | Planner 品質 | L2 分數勝過現況。資料層與編譯器已完成，缺的是拿分數證明選材有變好 |
| **M4** | Rough cut 品質底線 | §3 的五項指標全部達標 |
| **M5** | Skills 改版 | 主檔縮到一半以下；每條指引有對應 case |
| **M6′** | Feedback 好用化 | §8 的三項。三輪修改後使用者的手改不會被洗掉這點已經成立 |
| **M7** | B-roll | 覆蓋規則有測試；L3 rubric 分數提升 |
| **M8** | Render 擴充（多平台、重構圖、EDL 匯出） | 一份 plan 出三種比例 |

## 13. 等語料才能決定的事

方向都定了，剩下的是量的問題——沒有真實素材就只是在猜數字。
這些全部等 M1 的語料庫到位再定：

- **候選邊界的門檻值**：目前 `engine/sections.py` 的權重
  （停頓 0.45 / 語彙 0.30 / 話語標記 0.15 / 換場 0.10）、停頓飽和點、
  語彙窗口大小、每分鐘候選數，全是暫定值。在 talking head 和 vlog 上很可能不是同一組數字。
  調校會產生新的 `candidate_hash`，舊的段落建置不受影響，所以可以放心調。
- **`section` 的長度上下限**：目前刻意不強制，連警告都不給。
  太短切得瑣碎，太長就失去分層的意義——但該是幾秒，現在沒有根據可以說。
- **粗剪清理的門檻**：`engine/plan.py` 裡這五個全是暫定值——
  `SNAP_SECONDS` 1.0（剪點願意移動多遠）、`PAUSE_SECONDS` 0.6（多長的停頓算氣口）、
  `RETAKE_SIMILARITY` 0.85（兩句話多像算同一次重拍）、
  `HEAD_TRIM_SECONDS` 與 `TAIL_TRIM_SECONDS` 各 2.0（首尾最多修掉多少）。
  `PAUSE_SECONDS` 不只是感覺問題，它有一個下界：必須大於
  `2 * BREATH_SECONDS + MERGE_GAP_SECONDS`，否則切開的兩半會被 merge 接回去，
  整個階段變成看不見的空轉。調它的時候要連那條不等式一起看。
- **判官與人的一致度要多高才算可用**：校準集對不到什麼程度就得重寫 rubric。
- **L2 各項指標的權重**：切到字和長度超標都扣分，但不該扣一樣多。
- **畫質與音訊的門檻**：多糊算糊、多暗算暗、多晃算晃、底噪多高就該降噪，
  以及 `ClipKind.ACTION` 要從多少動態開始算。數字全部量得到了，
  但門檻在合成素材上訂出來只會是自己騙自己——真實素材的分佈長什麼樣還不知道。
  量測的取樣率（`PICTURE_FPS` 4、`CAMERA_FPS` 15、`faces.FRAME_FPS` 2）同樣是暫定值。
- **說話者切分的門檻**：`SPEAKER_DISTANCE` 0.5（兩個聲音差多遠算兩個人）、
  `MIN_SPEECH_SECONDS` 0.3、`MIN_PAUSE_SECONDS` 0.5、`SPEAKER_MAJORITY` 0.8
  （一段話要被一個人佔到多少才給標籤）。前三個決定會不會把同一個人拆成兩個，
  最後一個決定有多少片段會被留成沒有標籤——兩邊的代價不一樣，要有真的對談素材才調得動。
- **人臉偵測的分數門檻**：`faces.SCORE_THRESHOLD` 0.6。調低會把背景的路人也算進來，
  調高會漏掉側臉。哪一邊比較糟取決於這些數字被拿去做什麼。
- **語料庫的維度配比**：§11 的維度表列了要涵蓋什麼，沒說各佔幾支。
  等看到你手上實際有哪些素材再配。

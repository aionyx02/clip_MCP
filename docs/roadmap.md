# Roadmap — clip-mcp 2.0

1.0 把「時間軸 + FFmpeg」做穩了：工具正確、狀態持久、操作不會算錯秒數。
2.0 要補的是另一半——**判斷**。目前所有剪輯決策都在模型的腦袋裡即時發生，
沒有留下痕跡、無法重現、也無法評測。2.0 的核心是把這些決策變成資料。

```
                    Analysis
                       ↓
                Semantic timeline
                       ↓
                 Edit planner
                       ↓
             ┌─────────┴─────────┐
             ↓                   ↓
         rough cut           B-roll
             ↓                   ↓
             └─────────┬─────────┘
                       ↓
                    Preview
                       ↓
                  User feedback
                       ↓
                    Render
```

---

## 1. 為什麼需要 2.0

1.0 的資料只有兩層：**分析結果**（秒數區間 + 逐字稿）和**時間軸**（clip 的位置）。
中間沒有東西。從「這 42 分鐘素材裡有什麼」到「所以這 90 秒要放哪幾段」，
全靠模型在 context 裡一次想完。這造成四個問題：

| 問題 | 具體現象 |
|---|---|
| **裝不下** | 一小時素材的逐字稿就吃掉大半 context。`get_analysis` 一次只能讀 10 分鐘，模型得自己記住前面讀過什麼，素材一多就開始遺漏。 |
| **不可重現** | 同一批素材、同一句指令，兩次跑出來的剪法不同。沒辦法說「這次比上次好」。 |
| **改不動** | 使用者說「第三段太長」，模型只能回去改時間軸的秒數。當初「為什麼選這段」的理由沒有被記下來，所以改一個地方常常破壞另一個地方。 |
| **測不了** | 現有測試只能驗「工具有沒有算錯」，驗不了「剪得好不好」。指南裡寫的每一條剪輯建議，目前都沒有任何東西在檢查它有沒有被遵守、或者它到底有沒有用。 |

2.0 的作法是在中間插兩層**被持久化的**資料：

- **Semantic timeline**——素材裡有什麼，拆成可以被查詢的語意單位。
- **Edit plan**——要做什麼、為什麼這樣選，一份宣告式的文件。

有了這兩層，模型負責「選什麼、為什麼」，伺服器負責「怎麼排、算秒數」。
分工之後，前者可以被評測，後者可以被單元測試。

## 2. Analysis — 分析層

### 現況

`analyze_asset` 一次解碼同時跑 scene / black / freeze / silence 偵測，
再選擇性跑 faster-whisper 取得詞級時間戳，並把詞邊界吸附到實測的靜音邊緣
（`snap_words_to_silences`）。結果整份存進 `analyses` 資料表。

### 2.0 要補的

| 項目 | 用途 | 備註 |
|---|---|---|
| **鏡頭品質分數** | 曝光、清晰度、抖動程度，逐鏡頭一個分數 | 選材時先排除「拍壞的」，不必讓模型看圖判斷 |
| **說話者切分** | 對談、訪談類影片要知道誰在講 | diarization；決定 B-roll 蓋在誰身上、字幕要不要標人 |
| **人物存在與位置** | 畫面裡有沒有人、臉在哪、佔多大 | 直式重構圖、B-roll 覆蓋規則都需要 |
| **動態程度** | 這顆鏡頭是靜止的還是有事情在發生 | 節奏判斷、抓精華 |
| **音訊品質** | 底噪、削波、逐段響度 | 決定要不要降噪、哪段聲音不能用 |
| **視覺標籤** | 這顆鏡頭大致是什麼（海、食物、人臉特寫…） | 不內建視覺模型，改由客戶端模型描述後寫回，見 §3「視覺理解」 |

### 原則

- **一次解碼做完能做的所有事**。目前的 `detect_events` 已經是這個作法，新增的指標要併進同一個 pass，不要每加一個功能就多掃一次檔案。
- **本機優先**。偵測與轉錄一律在本機。唯一的例外是視覺理解（§3）：它靠客戶端模型
  讀縮圖，縮圖因此會離開本機。這件事必須是使用者明確開啟的，不能預設發生。
- **分析結果要帶版本**。換了 whisper 模型或改了偵測參數，要知道哪些素材的分析過期了，而不是默默沿用舊結果。

## 3. Semantic clips — 語意片段

這是 2.0 最關鍵的新概念，其他東西都建在它上面。

### 它是什麼

剪輯的最小決策單位不是「秒」，也不是「詞」，而是**一件可以獨立存在的事情**：
一句完整的話、一顆鏡頭、一個動作。semantic clip 就是這個單位。

它由現有分析結果交叉得出——逐字稿的句子邊界 × 場景切換 × 靜音區間——
每一段帶上它自己的描述與分數：

```
SemanticClip {
  id              穩定 ID，之後所有引用都用它
  asset_id
  level           utterance | section | topic，見下方「層級」
  source_range    來源檔的秒數區間
  kind            speech | action | ambient | silence | unusable
  text            這段說了什麼（speech 才有）
  speaker
  scores          品質、動態、清晰度…
  tags            視覺內容標籤，見下方「視覺理解」
  safe_in/out     安全剪點：往前往後各有多少餘裕不會切到字或動作
  parent/children 上下層的關聯，以及一句話橫跨數顆鏡頭時的關聯
}
```

`safe_in` / `safe_out` 是重點：它把「剪這裡會不會切到字」從模型的判斷變成資料。
1.0 的 skill 現在寫著「前後各加 0.1 / 0.15 秒，但要留在 silences 裡面」，
那是叫模型在 context 裡做算術——會算錯，而且沒人在檢查。

### 層級

粒度不是一個值，是三層。太細則數量爆炸，太粗則失去剪輯彈性，所以兩者都留：

| 層級 | 一個單位是 | 怎麼來的 | 拿來做什麼 |
|---|---|---|---|
| `utterance` | 一句話、一顆鏡頭 | 句界 × 場景切換 × 靜音 | 實際的剪點；`compile_plan` 只認這層 |
| `section` | 一個段落（講完一件事） | 相鄰 utterance 依題目與停頓合併 | 規劃結構、決定保留哪一段 |
| `topic` | 一個主題（可跨檔案） | section 依內容分群 | 素材總覽、提案、回答「這批素材有什麼」 |

模型平常讀 `topic` 與 `section`，只有要下剪點時才展開到 `utterance`。
一小時素材大約是數百個 utterance、數十個 section、個位數 topic——
最上層放得進任何 context，往下展開是隨選的。

### 視覺理解

不在伺服器裡塞視覺模型。客戶端本來就有一個多模態模型（Claude 等），
`view_frames` 本來就會產出標了時間的縮圖總覽——把這兩件事接起來就夠了：

1. 伺服器抽幀、壓縮、按語意片段切好（沿用 `view_frames` 的管線）。
2. 客戶端模型看圖，產出每段的描述與標籤。
3. 描述寫回 semantic timeline，成為 `query_clips` 檢索得到的資料。

第 3 步要有一道關卡：**寫回之前先讓使用者看過**。模型看圖會認錯東西，
而這些描述之後會被當成事實拿去選 B-roll。所以寫回的文本要可修正，
也要記下每個標籤的出處（偵測器算的／模型寫的／使用者改的）——
出處不同，之後能信任的程度就不同。

好處是不必安裝任何視覺模型、不吃 GPU，而且客戶端模型換得越好，理解就越好。
代價是縮圖會離開本機：README 目前寫著「素材不會上傳到任何地方」，
這個功能上線時那句話要跟著改，而且功能本身要是使用者主動開啟的。

### 為什麼要持久化

一小時素材的逐字稿放不進 context，但它的 semantic clip 摘要（數百筆，每筆一行）放得進。
選材因此從「自由發揮」變成「排序與挑選」——後者可以被評分。

### 新工具

| 工具 | 用途 |
|---|---|
| `build_semantic_timeline` | 從既有分析結果建出三層語意片段，存起來 |
| `query_clips` | 依層級、內容、說話者、種類、分數、時間查詢；回摘要不回全文 |
| `get_semantic_clip` | 取單筆細節（完整文字、逐詞時間、下層片段） |
| `frames_for_clips` | 產出某批語意片段的縮圖，交給客戶端模型看 |
| `set_clip_tags` | 把看到的描述與標籤寫回，帶出處；使用者確認後才呼叫 |

`get_analysis` 保留，但降級成除錯用途。日常剪輯改走 `query_clips`。

## 4. Timeline — 時間軸

### 現況

Project / Track / Clip 三層，14 種磁性編輯操作，樂觀鎖。這部分是 1.0 最穩的地方，
2.0 不重寫，只補三件事。

### 2.0 要補的

- **出身（provenance）**：每個 clip 記下它來自哪個 semantic clip、由 plan 的哪條決定產生。
  這樣才能回答「這段為什麼在這裡」，也才能在重新編譯 plan 時保留使用者手改過的部分。
- **鎖定（pinned）**：使用者手動調過的 clip 標記為鎖定，重新編譯 plan 時不被覆蓋。
  沒有這個，feedback 迴圈每跑一次就把使用者的修改洗掉一次。
- **結構標記（markers）**：時間軸上的段落標記（開場、主體、結尾、章節）。
  音樂換曲、B-roll 密度、字幕樣式都可以掛在段落上。

### 明確缺的功能

以下是業界基本盤，1.0 沒有，2.0 要補：

- **J / L cut**——聲音先進或後留，畫面另外切。訪談與對話剪輯沒有這個就是業餘的。
  需要 clip 的音畫分離偏移。
- **轉場**——目前只有淡入淡出黑。至少要有 cross dissolve。
- **變速**——`Clip.speed` 欄位早就在模型裡，但 `builder.py` 明確擋掉
  （`speed other than 1.0 is not supported yet`）。這是一個欄位到渲染鏈路的貫通工作，
  不是新設計。

## 5. Edit planner — 剪輯規劃器

「AI editing intelligence」實際落地的地方。

### 輸入 / 輸出

輸入：使用者意圖 + semantic timeline + 目標規格（長度、比例、平台、語氣）。
輸出是一份 **EditPlan**，不是一串操作：

```
EditPlan {
  goal            一句話：這支影片要做什麼
  target          長度、輸出比例、平台
  structure       [ {beat: "開場", 目標秒數, 要達成什麼}, ... ]
  selections      [ {semantic_clip_id, 放在哪個 beat, role, trim, 理由}, ... ]
  broll           [ {蓋在哪, 用哪段, 為什麼} ]
  music           選曲、進出點、ducking
  captions        要不要、樣式
  rejected        看過但沒用的段落，以及原因
}
```

`rejected` 不是裝飾。使用者說「那段講到 X 的怎麼沒放」，有這欄就能直接回答，
而不是重新分析一次。

### 編譯

`compile_plan(plan) → operations`，由伺服器把 plan 轉成 `apply_edits` 操作。
**這一步是確定性的、純函式的、可以寫單元測試的。**
所有秒數計算、磁性排列、淡入淡出長度、音樂對齊都在這裡，模型碰不到。

這個切分是整個 2.0 的槓桿點：

- 模型出錯的面積從「14 種操作的所有參數」縮小到「選哪些段落」。
- 「剪得好不好」變成一個可以評分的物件（plan），不必 render 出來用肉眼看。
- 同一份 plan 重跑必定得到同一個 cut。

### 誰來寫 plan

使用者沒有指定作法時，**由模型選**，plan 寫完再交給使用者判斷。
伺服器不給骨架、不預先決定結構——那會把剪輯變成填表格，
而「這支影片該長什麼樣」正是最需要判斷力、最不該被表格框住的部分。

伺服器負責的是**驗證**：引用的片段存在嗎、總長對得上目標嗎、
有沒有選到標成 `unusable` 的段落、各 beat 的秒數加起來合不合理。
驗證不過就退回並說明理由，不要默默修正——默默修正等於把判斷偷偷搬回伺服器。

plan **預設拿給使用者看**，翻成人話（幾段、各多長、為什麼這樣排），不是丟 JSON。
使用者可以說「不用看，直接剪」就跳過，但那是使用者關掉的，不是預設沒有。

### 新工具

`save_plan`、`get_plan`、`validate_plan`、`compile_plan`、`diff_plan`。

## 6. Rough cut — 粗剪

粗剪 = `compile_plan` 的產物 + 一組**機械性的清理**。這些清理不需要判斷力，
所以應該由程式碼做，而不是寫在 skill 裡叫模型注意：

- 去氣口：移除超過門檻的停頓，但每段之間留下一點呼吸
- 去重拍：同一句話講了三次，只留最後一次完整的
- 剪點吸附：所有剪點對齊到實測的靜音邊緣，不切字
- 避開壞幀：剪點不落在黑畫面、凍結畫面、對焦跑掉的那幾幀上
- 首尾修整：開頭不留「正要開口」，結尾不留「伸手關相機」

### 品質底線（可測）

這幾條要變成 benchmark 的自動指標，而不是指南裡的建議：

| 指標 | 目標 |
|---|---|
| 切到字的剪點 | 0 |
| 落在壞幀上的剪點 | 0 |
| 成片長度與目標的誤差 | < 10% |
| 必留段落覆蓋率 | > 90% |
| 必剔段落洩漏率 | 0 |

## 7. B-roll — 補充畫面

粗剪完成後的第二遍，不是同時做。

### 流程

1. 在粗剪上找需要蓋畫面的位置：聲音好但畫面弱、同一顆鏡頭停太久、剪點太生硬。
2. 從 semantic timeline 用標籤與文字檢索語意相關的畫面。
3. 蓋到上層 video track，`volume: 0`，底下的聲音繼續跑。

1.0 其實已經做得到第 3 步（上層軌道 + 不給 `layout` 就滿版），缺的是前兩步的判斷依據。

### 覆蓋規則

- 不蓋掉說話者正在做的關鍵動作（指東西、展示物品）
- 單段 B-roll 有最短與最長長度，太短像閃爍，太長會讓人忘記主線
- 一段話裡的 B-roll 密度上限
- 蓋的時機對齊句子邊界，不要在句中切進切出

## 8. Subtitles — 字幕

### 現況

`generate_subtitles` 從剪後時間軸產生字幕 → 使用者檢查 → `set_subtitles` 存起來
→ render 時 `burn_subtitles` 燒進畫面。已有依詞斷行與手機安全區處理。

### 2.0 要補的

- **綁 semantic clip，不綁絕對時間**。目前字幕存的是時間軸秒數，剪輯一改就全錯位，
  skill 只好寫「caption last」並要求重新產生。綁到語意片段之後，剪輯移動時字幕自己跟著走。
- **樣式預設集**：平台（YouTube / Reels / TikTok）各自的安全區、字級、描邊、位置。
- **雙語 / 逐字動態字幕**：短影音的標配。
- **講者標示**：多人對談時自動帶上名字或換色。

---

## 9. Audio — 聲音

### 現況

多音軌背景音樂、逐片段音量與淡入淡出、`duck_under_speech`、`fit_track` 對齊長度、
輸出統一正規化到 -14 LUFS。這塊 1.0 完成度相對高。

### 2.0 要補的

- **節拍對齊**：把視覺剪點對到音樂的節拍上。快節奏短影音的成敗幾乎全在這裡。
- **分段換曲**：跟著 timeline markers 換曲或換段落。
- **語音增強**：降噪、去嘶聲、高通；手機錄的素材尤其需要。
- **逐講者響度一致**：兩個人音量差很多時，各自給不同的 gain，而不是靠整體正規化擺平。
- **J / L cut 的音訊處理**：見 §4。

## 10. Preview — 預覽

### 現況

`preview_project` 產出 storyboard（剪後序列的縮圖拼貼），加上 480p 快速 render。

### 2.0 要補的

- **增量預覽**：只重算改動到的片段，其餘走快取。目前改一個剪點就要整支重跑。
- **差異呈現**：這次改了什麼——哪幾段換掉、長度差多少——用文字或圖示表達，
  而不是讓使用者自己比對兩張 storyboard。
- **帶聲音的預覽**：storyboard 看得到節奏卻聽不到，音樂對齊與 ducking 沒辦法只靠眼睛確認。

## 11. User feedback — 回饋迴圈

這是 1.0 完全沒有、而剪輯流程最重要的一環。

### 原則：回饋改的是 plan，不是 timeline

使用者說「第三段太長」時：

- **1.0 的作法**：模型去改時間軸上那個 clip 的秒數。plan 不存在，理由沒被記錄，
  下次重新產生就回到原樣。
- **2.0 的作法**：映射到 plan 裡對應的 selection → 改 plan → 重新編譯 → 保留 pinned 的部分。

這樣修改是累積的，而不是每次都從頭來過。

### 要做的

- 常見回饋語句到 plan 修改的對應表（太長 / 太趕 / 這段不要 / 開頭無聊 / 音樂太大聲…）
- 每次修訂留下版本，可以回退
- 一次回饋可能影響多處（「整體節奏太慢」不是改一段），要能表達全域性的調整

---

## 12. Render — 輸出

### 現況

背景 worker 輸出 MP4，可選 480p 預覽、燒字幕、響度目標，有進度與取消。

### 2.0 要補的

- **一次多平台**：同一份 plan 輸出橫式 / 直式 / 方形，直式靠追臉重構圖而不是硬裁中間。
- **章節與縮圖**：YouTube 章節、封面候選幀。
- **匯出給專業軟體**：EDL / OTIO / FCPXML。使用者想接手細修時，不該從零開始。
- **輸出前檢查**：黑幀、爆音、字幕出界、長度不符，在 render 前擋下來而不是之後才發現。

## 13. Skills 改版 — AI editing intelligence

### 現在的問題

`clip-editing/SKILL.md` 是 450 行的單一檔案，把工具說明、概念、工作流程、
對話語氣、操作對照表、預設值、錯誤處理全部塞在一起，每次都整份載入。
它是一份**知識傾倒**，不是一份**決策程序**。細節寫得越多，模型越難分辨
哪幾句話是這次該用的。

### 改版原則

1. **能寫成程式碼的就不要寫在 skill 裡。**
   「剪點要吸附到靜音邊緣」「音樂淡出要對齊結尾」這種沒有判斷空間的規則，
   屬於 compiler，不屬於指南。skill 只留真正需要判斷的部分。
2. **漸進式揭露。** 主檔只回答「現在該做什麼」，其餘按觸發條件載入。
   每個子檔要有明確的「什麼時候讀我」。
3. **一個檔回答一個問題。** 不要有「雜項」。
4. **每條指引都要有對應的 benchmark case。** 沒有 case 能證明它有用的指引，不寫。
   這條是為了防止指南隨時間膨脹成現在這樣。

### 規劃中的分工

| Skill | 回答的問題 | 何時載入 |
|---|---|---|
| `clip-editing` | 這句話對應哪個工具呼叫 | 每次 |
| `editing-intelligence` | 選哪些段落、怎麼排、多長 | 需要做剪輯判斷時 |
| `pacing-and-structure` | 節奏與結構（現有，保留並擴充） | 決定長度或結構時 |
| `platform-conventions` | 各平台的規格與慣例 | 指定平台時 |
| `feedback-handling` | 使用者的抱怨對應到 plan 的哪個修改 | 收到回饋時 |

現有的 `test_skill_resources.py` 雙向比對機制（工具與操作不得漂移）要保留，
並擴充到新的 skill 檔案。

## 14. Benchmark — 評測

**這是下一個工作項目。** 順序上先做評測、再做 planner，理由是：
沒有可重複的評分，skill 改版與 planner 的每一次調整都只能憑感覺，
而剪輯品質的感覺特別不可靠。

### 三層

| 層 | 測什麼 | 怎麼測 | 現況 |
|---|---|---|---|
| L1 工具正確性 | 操作有沒有算錯、render 出來對不對 | 現有 pytest | ✅ 已有 |
| L2 規劃品質 | 選材與結構好不好 | 對 plan 自動評分，不必 render | ⬜ 要做 |
| L3 成片品質 | 人看起來如何 | rubric + 人工抽樣 | ⬜ 要做 |

L2 是重點：它跑得快、可以每次 commit 都跑，而且因為 plan 是結構化的，
大部分指標可以自動算。

### 語料庫

目標 50–100 支影片，維度要鋪開，不能全是同一種素材：

| 維度 | 要涵蓋 |
|---|---|
| 類型 | talking head、vlog、教學、活動紀錄、產品開箱、多人對談 |
| 長度 | 30 秒到 60 分鐘都要有 |
| 語言 | 中文（台灣國語為主）、英文、中英混雜 |
| 聲音 | 乾淨收音、環境吵雜、無人聲、只有音樂 |
| 畫面 | 直式與橫式、手持與固定、光線好與壞 |
| 品質 | 刻意包含拍壞的素材（失焦、黑畫面、誤錄） |

### 每支影片配的東西

素材本身不是題目，**素材 + 指令 + 參考標註**才是：

- 一到三句使用者指令（從明確到含糊都要有，含糊的才測得出判斷力）
- 標註：必須保留的區段、必須剔除的區段、可接受的剪點範圍
- rubric：這支影片剪成什麼樣算好，分項給分
- 不是唯一解。好的剪法不只一種，所以評的是「有沒有踩到地雷」與「有沒有抓到重點」，
  不是「跟標準答案有多像」

### 自動指標

- 必留段落覆蓋率 / 必剔段落洩漏率
- 成片長度與目標的誤差
- 切到字的剪點數、落在壞幀上的剪點數
- 剪點與最近安全邊界的距離分佈
- 成本：工具呼叫次數、token 用量、wall-clock 時間

### 迴歸

每次改 skill、planner 或分析參數就跑一次，留下分數。
分數退步就是 regression，跟測試失敗同等對待。

## 15. 里程碑

| 階段 | 內容 | 完成標準 |
|---|---|---|
| **M0** | 1.0：時間軸、分析、字幕、音訊、render | ✅ 已完成 |
| **M1** | Benchmark 骨架與語料庫（50–100 支） | L1 接上 CI；L2 指標能對現況跑出基準分數 |
| **M2** | Semantic timeline | 三層片段建得出來；一小時素材的 `topic` / `section` 摘要放得進 context；視覺描述能寫回並標出處 |
| **M3** | Edit planner + compile | plan → operations 純函式，有單元測試；L2 分數勝過現況 |
| **M4** | Rough cut 品質底線 | §6 的五項指標全部達標 |
| **M5** | Skills 改版 | 主檔縮到一半以下；每條指引有對應 case |
| **M6** | Feedback 迴圈 | 三輪修改後使用者的手改不會被洗掉 |
| **M7** | B-roll | 覆蓋規則有測試；L3 rubric 分數提升 |
| **M8** | Render 擴充（多平台、重構圖、EDL 匯出） | 一份 plan 出三種比例 |

M1 與 M2 可以並行：語料庫的收集與標註不依賴程式碼。
M3 之後每一階段都以 benchmark 分數作為完成標準，不以「功能做完了」作為標準。

## 16. 已定案的設計決定

| 題目 | 決定 | 細節 |
|---|---|---|
| semantic clip 粒度 | 三層：`utterance` / `section` / `topic` | §3「層級」 |
| 視覺理解要做到多深 | 不內建視覺模型。伺服器切片壓縮 → 客戶端模型描述 → 使用者確認後寫回後端 | §3「視覺理解」 |
| EditPlan 由誰產生 | 使用者沒指定就由模型選，寫完交使用者判斷；伺服器只驗證，不給骨架 | §5「誰來寫 plan」 |
| plan 要不要給使用者看 | 預設給看，翻成人話；使用者可以拒絕 | §5「誰來寫 plan」 |
| 向後相容 | 不維持工具介面相容，直接改 | 下方「向後相容」 |

貫穿前四項的同一個取捨：**判斷留給模型與使用者，計算留給伺服器**。
伺服器不替模型決定結構，也不把模型寫的東西當成既成事實——
視覺描述要人確認過才進資料庫，plan 要人看過才編譯。

### 向後相容

這台 server 沒有外部使用者，所以 2.0 **不維持工具介面相容**：
`get_analysis` 降級、新增 `query_clips` 與 plan 系列，都直接改，
不留舊工具當轉接。維護兩套工具名的成本沒有人需要付。

資料層則分三種情況處理：

| 層面 | 作法 | 成本 |
|---|---|---|
| 舊專案的欄位 | 什麼都不做。儲存是 JSON 字串、Pydantic 欄位都有預設值，加欄位天生相容 | 免費 |
| 舊專案的字幕 | 標成「需重新產生」，不寫遷移程式 | 幾乎免費 |
| 舊的分析結果 | 用 §2 的分析版本標記，只有用到新指標的功能才要求重跑 | 一個欄位 |

字幕是唯一**語意**改變的地方（§8 從絕對時間改成綁 semantic clip），
所以是唯一需要動手的。既然沒有外部使用者，就不值得為它寫遷移程式——
舊專案重新產生一次字幕就好。

## 17. 還沒決定的事

以下兩項不擋 M1（benchmark），但 M2 動工前要有答案：

- **`section` 與 `topic` 怎麼切出來**。§3 只寫了「依題目與停頓合併」「依內容分群」，
  那是結果不是作法。純規則（停頓長度 + 場景密度）便宜但切不準題目邊界；
  交給模型切則準但每次結果不同，而 semantic timeline 是要被持久化與評測的東西，
  不穩定會直接汙染 benchmark 分數。可能要規則先切、模型只做合併與命名。
- **L3 人工評分誰做**。50–100 支影片逐支照 rubric 評分是實打實的人力。
  是全部評、還是只抽樣？多久評一次？如果沒有人力，L3 就只能是每個里程碑
  抽幾支來看，不能當成迴歸指標——那 §15 里程碑的完成標準就要只靠 L2。

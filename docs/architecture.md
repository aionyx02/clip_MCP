# 架構

分三層，由外而內：`server.py` 只負責 MCP 介面與參數驗證，`engine/` 是不依賴 MCP
的影音引擎，`models/` 是純資料與規則。`storage/` 橫跨其上，負責持久化。
引擎層可以單獨拿去用，不必掛在 MCP 底下。

## 幾個貫穿全域的約定

- **時間單位**：模型與工具之間一律用秒（float）。`source_range` 是來源檔的秒數，
  `timeline_in` 是剪輯後時間軸的秒數。
- **樂觀鎖**：`apply_edits` 必須帶 `expected_version`。版本不符就整批不套用，
  呼叫端重讀 `get_project` 再重試。失敗的呼叫不會留下半套狀態。
- **一次解碼量完**：解碼一支長片是整個分析裡最貴的一件事，所以要幀的東西全部掛在
  同一個 filtergraph 上：偵測分支維持原本的畫面與聲音，量測分支用 `split` 接出去，
  各自用自己的取樣率跑（畫面 4 fps 量曝光／對比／模糊／動態，另一條 15 fps 量鏡頭抖動，
  聲音每秒一格量響度／峰值／底噪／削波）。亮度分支強制 `out_range=full`，
  否則 16-235 的一般素材量出來黑是 0.06、白是 0.92，而且跟全範圍的檔案不能比。
  濾鏡把結果寫進檔案再回頭解析，
  所以寫進 filtergraph 的路徑一律過 `escape_filter_path`——一個普通的 Windows 路徑
  本身就是 filtergraph 語法。
  **量測不是評價**：伺服器只給數字，不說哪顆鏡頭算太暗或太晃——那取決於這顆要用來幹嘛。
  數字落到語意片段的 `scores` 上，`query_clips` 就能直接下界限。
  **怎麼合併由分數自己決定**（`semantic.SCORE_RULES`）：分貝是對數的，
  直接平均會讓「九秒人聲加一秒靜音」從 -20 dB 變成 -30 dB，所以響度換成能量再平均；
  峰值與削波取最大值（發生過就是發生過，平均掉就看不到了）；底噪取中位數
  （取最小值會被那一秒數位靜音講成一支超安靜的錄音）。其餘才是時間加權平均。
  同一張表也決定每個分數留幾位小數，以及它是「描述內容」還是「描述怎麼拍的」——
  前者在沒有它的片段上算 0（沒人講話就是真的沒有語音），後者在沒量到的片段上不算數，
  而搜尋結果也只帶前者。段落層（`sections.py`）用同一套規則，不另外寫一份，
  所以取中位數也是**依時間加權**的：一個段落由二十句半秒的話加一顆一分鐘的鏡頭組成時，
  它聽起來是那一分鐘，不是那二十句。
  **量不到就留白**：沒取到樣的鏡頭不產生量測、全黑畫面的 `blur` 是 null，
  而全靜音的那一秒會記成 `-120 dB` 而不是消失——「沒量到」跟「量了是靜音」
  必須看得出差別，這跟計分卡的 `unmeasured` 是同一條規矩。
- **模型是專案資料，不是機器安裝**：所有權重（含 whisper 的 `download_root`）都指到
  工作區的 `models/`，不寫家目錄的共用快取——刪掉工作區就等於刪掉模型。
  每個模型釘住 SHA-256，先下載到暫名、驗過才搬進位置，所以中斷的下載不會留下
  下一次會誤認的半成品。下載失敗**讓整個工作失敗並說明是哪個模型**：
  下載失敗是會過去的問題，值得重試；默默產出一份少了一項量測的分析，
  留下的卻是一個看起來做完了的東西。
- **要幀的東西都掛在同一次解碼上**：人臉偵測需要整張畫面，而沒有濾鏡會把畫面交回來，
  所以那一個 pass 順便把小尺寸縮圖寫成檔案（`-f image2`），`faces.py` 事後讀回來。
  **這些檔案是鷹架不是產出**：縮圖一小時一兩百 MB，加上逐幀／逐秒的 metadata 與
  抖動的 transforms 又約 35 MB，所以 `discard_scratch` 在 `analyze_media` 的 `finally`
  裡把它們全部刪掉——包含掃描中途被取消的那條路徑，那正是最可能取消的時刻，
  也是沒開轉錄時唯一的階段。只留 `detect.log`，它只有幾 KB，而且分析失敗時就靠它。
  這是為了守住「素材只解碼一次」，不是為了省事。
  **說話者切分是唯一的例外，而且它不解畫面**：`read_samples` 只 map 音訊串流
  （`-f f32le` 這種純音訊輸出不會選到視訊），實測 60 秒 1080p 只花 0.07 秒，
  一小時約 4 秒。要避開它就得把 16 kHz 音訊另存一份，一小時 115 MB 的暫存檔換 4 秒 CPU，
  不划算，所以沒做。
- **剪點那一幀不算數**：一顆鏡頭的第一個取樣點，它的 `YDIF` 是跟**前一顆鏡頭的最後一幀**
  比出來的，抖動的第一筆位移同理。那是剪接的大小，不是這顆鏡頭裡發生的事——
  實測黑畫面接純白畫面時，那顆完全靜止的白鏡頭會回報 0.107 的動態。
  所以 `motion` 與 `shake` 都從第二個取樣點起算，樣本不夠的鏡頭回 null 而不是 0。
- **標籤只在自己的檔案裡有意義，接起來是另一層的事**：diarization 的 `S1` 出了那支檔案
  就什麼也不是，所以同一場訪談用兩台機拍會回報四個人。`analyze_asset` 因此每個標籤
  留一份嵌入向量（`MediaAnalysis.voices`，一個標籤一份而不是一段一份：同一個標籤的
  段落本來就是同一個人，合起來量比任一段穩，也不會讓一小時的訪談背幾百個向量），
  而**接起來發生在語意時間軸建置時**——那是第一個同時看得到多支檔案的地方。
  接起來的標籤叫 `V1`／`V2`，跟各檔自己的 `S1`／`S2` 用不同的字母，免得有人看錯。
  比的是 cosine 距離，因為嵌入向量的長度帶著音量：同一個人靠近麥克風錄，
  用別的距離量都會變遠，用這個量不會。走訪順序固定（檔案依 ID、標籤依名字），
  所以同一批素材永遠接出同一組標籤——依誰先講話來分配的話，答案會取決於分析被讀進來的順序。
- **標籤要賺來的**：`speaker_at` 只有在一個聲音佔掉該段**講話時間**八成以上時才給標籤，
  中間換人的片段回 `None`。段落裡的靜音不算在任何人頭上，所以中間有停頓的一句話
  仍然屬於講完它的那個人。標籤會上字幕、會進剪輯，錯的標籤比沒有標籤糟。
  它住在 `semantic.py` 而不是 `diarize.py`：它只是讀已經存好的段落做算術，沒有模型，
  而且那個八成的門檻一改就會改掉每個片段的標籤——放在 `semantic.py` 才受
  `DERIVATION_VERSION` 管得到，放在別的檔案就只能靠人記得。
- **分析配方**：每份分析都帶 `recipe`（版本、偵測參數雜湊、用過的語音與說話者模型）。
  換了門檻或換了 whisper 模型，舊分析不會壞掉，只是它回答的問題跟新的不完全一樣，
  所以 `get_analysis`、`list_assets` 與 `build_semantic_timeline` 一律**回報過期但不擋**——
  為了改一個數字就重跑一小時素材，比拿兩個稍微不同的量測比較更糟。
  沒有 libvidstab 的機器量不到抖動，這件事也算在配方裡。
  沒跑過的模型不會讓分析過期——沒開說話者切分的素材，換了說話者模型也與它無關。
  節拍偵測走同一條路（`rhythm_model`，名字裡帶著它每個參數的指紋），
  所以調節拍的門檻只會讓配樂過期，不會讓每一支素材都過期。
- **語意時間軸**：`engine/semantic.py` 把 `MediaAnalysis` 推導成語意片段，是一支
  **純函式**——句界、換場、靜音都已經在分析結果裡，所以不碰模型、不抽樣，
  同一份分析永遠得到同一批片段。`safe_in` / `safe_out` 是這層的重點：它把
  「剪這裡會不會切到字」從模型的判斷變成量出來的資料。
  建置以輸入雜湊釘住（涵蓋各素材分析內容與 `DERIVATION_VERSION`，但不含
  `analyzed_at`），timeline id 與 clip id 都由該雜湊推導，所以同一批素材在任何機器上
  都得到同一組 ID；重建不變的輸入會原樣取回既有建置，引用不會失效。
- **段落裁決**：`section` 不能純靠規則找出來，但可以縮小範圍。`engine/sections.py`
  用實測訊號（停頓長度、語彙翻新程度、換場密集度、話語標記）**過量產生**候選邊界，
  模型只能在候選裡挑選與命名，伺服器驗證的是「回來的 ID 在不在清單裡」以及
  「這些段落有沒有把素材蓋滿」——是成員資格檢查，不是解讀。
  模型最糟的錯誤因此是段落分得不好，**不可能是切到字**，因為每個候選本來就長在
  實測的靜音邊緣上。候選的權重與門檻是暫定值，記在 timeline 的 `candidate_hash` 裡，
  之後靠語料調校會產生一份明顯不同的新建置，不會把已經談定的段落底下的邊界悄悄挪走。
- **topic 是標籤不是層級**：主題可以不連續、可以跨檔案，沒有自己的區間可以當成 clip，
  所以它是 section 上的一個 `topic` 欄位，同一個標籤在不同檔案的 section 上就把它們串起來。
- **plan 編譯器**：`engine/plan.py` 是這套設計賴以成立的確定性那一半。模型決定選哪些片段、
  為什麼；從那裡開始的每一件事——剪點落在哪、留多少呼吸、哪些併成一段、成片多長——
  都是 plan、語意時間軸與**乾淨剪點**的純函式。乾淨剪點（`engine/semantic.clean_cuts`）
  是「這個檔案可以在哪些秒數下刀而不切斷詞」，同樣由分析結果純函式推導出來；
  編譯器拿到的是數字，不是逐字稿——讀逐字稿是解讀，那會讓編譯器不再是純函式。
  `head` 與 `tail` 這兩個會落在任意秒數的 trim 因此會吸附到最近的詞邊界；
  有呼吸的邊界本來不該需要，但呼吸是從靜音偵測量的、詞是從辨識來的，兩者會不一致，
  所以呼吸把剪點推進詞裡時會把那口呼吸還回去。
  **四個清理階段**接在選材之後，順序是定死的：去重拍（同一句連著講兩次以上，
  只留最後一次講完的）→ 去氣口（把一顆鏡頭中間超過 `PAUSE_SECONDS` 的死空氣切掉，
  兩側各留一口呼吸）→ 首尾修整（開頭不留「正要開口」、結尾不留「伸手關相機」）→
  避開壞幀（剪點落在黑畫面或凍結畫面上就移開）。先去重拍，因為沒必要替一個
  即將被丟掉的 take 清氣口；壞幀放最後，它對前面每個階段造出來的邊界有最終決定權。
  每個階段都**只在拿得到 `CleanCuts` 時才動**（不知道就不清），而且動了就報一句話——
  改了別人的剪接就要講。這四個階段的門檻全是暫定值，列在 roadmap §13。
  **每個新剪點都要先吸附**：`_settled` 把任何新邊界移到真的能下刀的秒數上。
  這不是保險，是實測需求——第一版直接在靜音邊緣切，在三支真實素材上把切到字的
  剪點從 0／1／0 變成 6／14／8，因為詞的結束時間經常延伸進被判為安靜的那一段。
  吸不到就整個氣口留著並回報，不硬切。
  `trim` 是**封閉集合**（`full` / `keep` / `head` /
  `tail` / `tighten`），沒有自然語言指令：編譯器一旦需要解讀句子就得在裡面塞一個模型，
  同一份 plan 就不再決定同一個結果。驗證不過的 plan 原樣退回並附理由，不默默修正。
- **出身與鎖定**：`compile_plan` 產生的每個 clip 都記下 `from_plan_id` 與
  `from_clip_ids`（它是由哪些語意片段合併而成的）。出身不經過工具介面——
  操作套用完之後由 `_apply` 的 stamp 直接寫上去，所以呼叫端碰不到它。
  **手改就是鎖定**：`trim_clip` / `move_clip` / `split_clip` / `reorder_clip` /
  `set_clip_look` / `set_clip_audio` 動到一個有出身的 clip，它就自動 `pinned`，
  沒有人需要記得多下一個指令——忘記的代價是回饋迴圈每跑一次就洗掉使用者的工作。
  重新編譯時，pinned 的 clip 連同它被改過的 source_range 與設定原樣保留，
  只有在序列裡的位置由新的 plan 決定；配對靠的是 `from_clip_ids` 完全相同。
  如果新 plan 已經不再用到某個 pinned clip 的素材，**整個編譯被拒絕並列出擋路的 clip**——
  丟掉使用者的工作比停下來糟。編譯只擁有主序列、音樂軌與 B-roll 軌，其他軌道原封不動。
  釘住的配對靠 `from_clip_ids`，所以三種 clip 各有自己的身分：主序列是它合併了哪些語意片段，
  B-roll 是「蓋的素材 + 被蓋的位置」這一對，音樂是空的（它不由任何語意片段組成）。
  空的那一個仍然算「在新 plan 裡有位置」，只要 plan 還有音樂——否則釘住配樂再重新編譯
  會被自己的檢查擋下來。
- **B-roll 是 plan 的第二遍，不是第二種 plan**：`EditPlan.broll` 的每一筆說
  「用哪個語意片段的畫面、從哪個語意片段開始蓋、蓋幾秒」，編譯成 `broll` 軌上一個
  `volume: 0` 的滿版 clip。**位置用語意片段錨定而不是用秒數**，因為時間軸每次重新編譯
  都會動，釘在秒數上的覆蓋下一次就蓋錯地方。開始點因此天生落在句子邊界上；
  結束點是人選的長度，編譯器**回報**它有沒有切在句子中間而不是替它延長——延長就是在決定
  成片多長，那跟 §3 的「句子沒講完」是同一條界線。
  「這一刻在成片的哪裡」是問秒數不是問選材（`_in_cut`），所以被 merge 併進同一個視窗的
  兩句話仍然是兩個可以切進去的位置——這才讓一顆長鏡頭能被蓋一部分而不是只能整顆或不蓋。
  四條覆蓋規則（單段長度、一個 beat 的覆蓋上限、不得互相重疊、不得蓋掉
  `hold_picture` 的選材）全部在編譯器裡，違規就退回並說明理由。
  `propose_broll` 只提供**位置**候選，用的是兩個純長度的訊號（一顆鏡頭停太久、
  連續幾顆來自同一個檔案）；找什麼素材來蓋是 `query_clips` 與模型的事。
  **候選是建議，不是成員資格檢查**——這裡跟 `sections.py` 不一樣，是刻意的。
  段落必須綁在候選上，因為「這是不是一個乾淨的邊界」只有候選清單答得出來，
  離開清單就可能切在字中間。B-roll 不是：切入點不得落在句中、長度、beat 覆蓋上限、
  不得重疊、不得蓋掉 `hold_picture`——全部都能直接檢查，所以模型蓋在哪裡錯了，
  錯的仍然只是選擇，不會是算術。候選清單在這裡回答的是「哪裡值得蓋」，那是品味，
  綁死它只會擋掉合理的選擇。也因此不需要 `candidate_hash`：要釘住的東西
  `timeline_input_hash` 已經釘住了。
- **配樂是一串 cue，每個 cue 綁在一個 beat 上**：`MusicPlan.cues` 的每一筆說
  「從哪個 beat 開始、放哪首、從歌的第幾秒進」，跑到下一個 cue 進來為止。
  跟 B-roll 同一個理由用 beat 錨定而不是秒數：beat 開始在哪由編譯決定，
  換曲因此跟著它所屬的那一段走。`asset_id` 為 null 就是「這段不要音樂」——
  音樂軌上留一段空，而不是放一段靜音的 clip。歌比那一段短就**循環回 cue 進來的那一秒**，
  不是回到歌的開頭：cue 選了那個點，跳過的前奏第二次也一樣不受歡迎。
  淡入淡出屬於 cue 而不是每一次循環；兩個 cue 頭尾相接，一邊淡出一邊淡入，
  因為一條軌同時只放一個 clip，兩首不會疊在一起。之前的 `fit_track` 做法只處理一首歌，
  所以編譯器改成自己算好每一段、用 `add_clip` 放在絕對位置上。
- **剪點對拍是 cue 的選項，而且只准在靜音裡移動**：節拍在分析時量一次
  （`engine/rhythm.py`，只對有聲音沒畫面的檔案——對人講話跑節拍偵測，會在音節裡找到一個拍），
  編譯器拿到的只是秒數。`cut_on_beat` 的 cue 底下，每個畫面剪點靠**改變前一個視窗的結尾**
  移到最近的拍上，所以後面每個剪點都跟著平移——因此依序結算，每一個都對著前面已經落定的位置算。
  它得到的寬容比「移出詞中間」少得多，因為這是品味不是修正：不得早於最後一個詞加一口呼吸、
  不得碰到下一個詞的呼吸、不得露出壞幀、不得跑進後面同一支檔案的視窗，
  也不得移超過 `BEAT_SNAP_SECONDS`。最近的拍到不了就試另一邊那個，兩邊都不行就原地不動並回報。
  **沒有逐字稿的素材一律不動**：`CleanCuts.transcribed` 就是為了這件事加的——
  轉錄過但沒人講話的檔案和沒轉錄的檔案，`words` 都是空的，但前者可以放心移、後者不知道會不會切到字。
  歌本身也要從拍上進：`cut_on_beat` 的 cue 會從 `start` 之後的第一個拍進來，
  否則整條拍格就從一個不是拍的地方算起。換曲的那個剪點對的是**出去的那首**的拍，
  新的那首本來就從那個剪點、從它自己的拍上開始，所以兩邊都對得上。
  拍格照 `music_beds` 鋪的方式循環，所以循環之後的剪點仍然落在拍上。
  B-roll 的切入點不對拍——它綁的是句子邊界，那一條比拍重要。
- **節拍偵測的兩個實測教訓**：第一版在單一頻率 bin 上算 flux，穩定的正弦波會跟 frame 的步進
  產生拍頻，嘶聲會讓每個 bin 閃爍，加總幾百個 bin 就像有脈動——量出來 200Hz 的純音有 115 BPM。
  改成先在 24 個依音高等距的頻帶內加總再取對數，雜訊平均掉，鼓組與無脈動的差距從重疊
  拉到 5 倍對 1.7 倍，`MIN_CONTRAST` 才訂得下去。第二個是 0.4 秒的拍：週期不是整數個 frame，
  一個 frame 寬的 onset 互相錯開，反而是兩倍週期看起來對得比較齊，於是回報成半速；
  先把 envelope 用約 20ms 的高斯模糊一下就好了。兩件事各有一個測試釘住。
- **一份剪輯出好幾種比例，靠的是 render 時換尺寸，不是複製專案**：`render_project` 的
  `frame` 只在那一次 render 給專案一個新尺寸（保留短邊：1080p 不管直橫都是短邊 1080），
  存著的專案不動。所以三種比例永遠是同一份剪輯，改一次剪輯三個版本一起變。
  換了比例的畫面仍然是「放大到蓋滿再裁」，差別只在**從哪裡裁**：`engine/reframe.py`
  用分析時存下的逐秒人臉位置決定裁切窗的中心，builder 把它寫成 `crop` 的逐幀表達式
  （`if(lt(n,…))` 串起來的分段常數），所以不需要知道來源尺寸以外的任何東西。
  **臉移出去時選的是切，不是推。** 推是一個沒有人拍過的運鏡，而且由一秒兩次的偵測驅動，
  不是追不上臉就是跟著每一次量測抖動；切到新的構圖是剪直式版本的人手動在做的事，
  看起來就是一個剪接。所以裁切窗在臉還舒服地待在裡面時完全不動，臉靠邊待滿
  `REFRAME_HOLD_SECONDS` 才切；太靠近鏡頭本身的剪點（`REFRAME_MIN_SHOT_SECONDS`）時
  **延後而不是放棄**——第一版是放棄，結果一個一開場就走到旁邊的人整顆鏡頭都在畫面外。
  開場構圖取第一個看到臉的那一秒，不取中位數：中位數會把兩個位置平均成中間那個沒人的地方。
  只跟有餘裕的那一軸：寬的鏡頭放進窄的框跟橫向，高的放進寬的框跟縱向。
  資產因此多記了實際畫面尺寸（`Asset.width` / `height`，手機直拍的旋轉已經算進去），
  舊資產第一次用到時才補量並存回去。storyboard 與封面用同一份裁切中心，
  所以 render 前看到的就是 render 出來的構圖。
- **出片前檢查是事實不是判決，但會擋**：`engine/delivery.check_delivery` 找四件成片裡會被
  看出來的事——黑或凍結的來源畫面真的上了螢幕（被滿版 B-roll 蓋掉的不算，子母畫面不算蓋掉）、
  錄音本身爆掉（峰值貼頂且波形被削平；調小聲救不回來）、字幕高到超出畫面、
  長度離 plan 要的太遠。`render_project` 有發現就**拒絕正式 render**，
  要使用者聽過之後由 `allow` 明確點名放行哪幾類——跟 plan 驗證「退回並說明理由」同一條原則，
  只是這裡的東西可能是刻意的（黑畫面停頓、使用者寧可長一點），所以留一個明確的出口
  而不是永遠擋死。預覽不擋，因為預覽本來就是拿來看的。
  **字幕出界的定義是幾何，不是品味**：每行本來就會斷到符合寬度，所以唯一還會出界的是高度
  （預設一次一行，所以實際上只剩雙語字幕會疊高），由 `caption_geometry` 算——同一個函式也拿去畫 ASS，兩邊不可能對「放不放得下」有不同答案。
  做這個的時候順便抓到一個真的 bug：講者名字是在斷行**之後**才加在前面的，
  中文沒有空白讓 libass 再斷一次，所以第一行會被名字推出畫面。現在名字先算進寬度再斷行。
- **章節就是 markers**：plan 編譯時每個 beat 寫一個 marker，`get_chapters` 把它讀成章節，
  render 時也用 ffmetadata 寫進 MP4（播放器直接讀得到）。YouTube 的三條規矩
  （0:00 開始、至少三段、每段至少十秒）是平台規則，跟字幕預設集同類，收在 `delivery.py`；
  不符合就回報，不自動合併——合併或改名段落是在改影片。
  **封面候選是 argmax 不是門檻**：每顆鏡頭一張，取臉最大的那一秒，沒有臉就取最清楚的那一段，
  永遠不取黑或凍結畫面。選哪一張是模型與使用者的事。
- **匯出只帶剪輯本身，而且照實說少了什麼**（變速、OTIO 的轉場、FCPXML 的音量、
  來源檔 timecode 後來補上了，見 roadmap §9）：`engine/interchange.py` 手寫 EDL／OTIO／FCPXML，
  不加依賴——三種都是小而穩定的文字格式，用到的部分更小。帶過去的是每個 clip 的進出點、
  位置、軌道，與 markers；這個伺服器自己畫的東西（變速、轉場、調色、音量與淡入淡出、
  語音修復、子母畫面位置、字幕）一律不帶，`left_behind` 逐項列出這支剪輯用了哪些，
  免得使用者在別的軟體裡才發現不對。字幕另外輸出 SRT。
  開發時用 OpenTimelineIO 0.18 與它的 CMX3600、FCPXML adapter 實際讀過三種輸出
  （軌道、空隙、markers、每個 clip 的 frame 數都對），但那是一次性的驗證，
  測試裡只自己解析——不為了測試把 OTIO 加進依賴。
  EDL 只有一條畫面軌，timecode 以最接近的整數 fps 計、一律非 drop frame：
  frame 對得上，但 29.97 時會比時鐘慢一點點。來源檔自帶的起始 timecode（專業攝影機常見）
  沒有讀，一律從 0 算——接手的軟體若以檔案內 timecode 對位會錯開，等有人遇到再處理。
- **預覽的快取鍵是配方，不是身分**：plan 原本寫的是用 piece 的 `from_clip_ids` 當鍵，
  實作時改成**那顆畫面的 FFmpeg 配方本身**——輸入參數、每一個濾鏡、來源檔的大小與修改時間——
  的雜湊。身分當鍵會漏掉手改：同一段素材被手動調色或重構圖，身分沒變、畫面變了；
  配方當鍵則任何會改變畫面的東西都自動換鍵，兩個專案用同一顆鏡頭同一種方式時還能共用。
  預覽因此分兩步：先把快取裡沒有的畫面各自 render 成一個小檔（寫到暫名、完整了才搬到正名，
  中途取消不會留下半個檔案被下次撿去用），再把快取的畫面接起來、疊上層軌、混聲音。
  **聲音每次都重混**：它便宜，而且 ducking 與響度正規化看的是整支，快取一段段的聲音
  反而會錯。預覽直接用短邊 480 的尺寸 render，不再是全尺寸合成完才縮小。
  十四天沒用到的快取畫面會被清掉——那是家務不是判斷，要用時幾秒就重算回來。
- **修掉的同步 bug**：做快取時把「畫面」與「聲音」的輸入拆開，才發現一個從轉場加入時就在的
  錯：有轉場的 clip，聲音一直是從畫面的輸入讀的，而畫面的輸入為了轉場的 run-up 提早開始，
  所以那個 clip 的聲音**晚了整整一段轉場長度**（1 秒溶接就晚 1 秒）。現在有 run-up 的 clip
  一律從自己的進點另外讀聲音，並有一個 render 後量頻段的測試釘住——拿掉修正它會失敗。
  同一次也讓上層軌的 clip 用跟主序列同一條畫面鏈，所以上層軌的變速現在真的會變速。
- **差異畫在 storyboard 上**：`piece_changes` 用重新編譯配對手改 clip 的同一個身分
  （`from_clip_ids`）把兩份 plan 編出來的視窗配起來；被氣口切成兩半的視窗帶著同一組 ID，
  所以依序配。在兩邊都有的視窗裡，**還維持舊順序的最長那一串算沒動**，其餘算搬過——
  這才是人會說的「把一顆搬到前面」，而不是「後面每一顆都變了位置」。
- **聲音預覽是給看不見聲音的人看的**：模型聽不到，storyboard 也沒有聲音。`preview_sound`
  用同一套混音只 render 聲音（不解碼任何畫面），另外分出兩軌：素材本身的聲音，
  與 ducking 之後的音軌。逐 0.1 秒量兩軌的電平，畫成一張圖（剪點、段落都標上），
  逐段報出人聲多大、講話時配樂低多少、空檔時配樂回來多少。量的是正規化之前的電平，
  所以要看的是兩者的差而不是絕對值。混好的聲音另存成檔案給使用者聽。
- **配樂的釘住修好了**：編譯出來的配樂之前全部用空的身分，重新編譯的檢查放它過、
  編譯卻不把手改的設定放回去——手動調小聲的配樂重編之後會被默默調回來，
  違反了「手改不會被洗掉」。現在每一段配樂的身分是「哪個 cue、第幾次循環」，
  像 B-roll 一樣配對並放回手改的設定；更早編譯的配樂沒有身分，當作第一段。
  手動把某段拉長到撞上下一段時，重新編譯會被退回並說明。
- **plan 的每一版都留著，回退是往上疊一版**：`plan_versions` 表每次 `save_plan`、
  `amend_plan`、`revert_plan` 都寫一筆，在同一個交易裡寫，所以不可能存了 plan 卻漏了歷史。
  回退不是倒帶：舊版的內容被存成**新的一版**，所以「回退」本身也能被回退，
  歷史永遠不會比做過的事短。每一版帶一個 note——使用者自己說的話，加上這一版的修正做了什麼——
  所以翻歷史時看得到每一輪回饋是為了什麼。遷移時把現有 plan 的當前版本補進歷史；
  之前的版本本來就沒存，找不回來。
- **全域修改是 plan 的設定，不是逐段改**：「整體節奏太慢」會同時動到每一個剪點，
  寫成對每個選材的 trim 既囉唆又會在下一次加選材時漏掉。所以 `EditPlan.pacing`
  （`pause_seconds` 多長的靜音要拿掉、`breath_seconds` 每個剪點留多少空氣）是 plan 的欄位，
  編譯器在每一個清理階段都用它，取代原本寫死的 `PAUSE_SECONDS` / `BREATH_SECONDS`
  （那兩個常數現在是預設值）。兩者之間那條不等式——拿掉一個氣口後兩邊各留一口呼吸，
  剩下的要比 merge gap 長，否則會被接回去變成看不見的空轉——在 `check_plan` 裡擋，
  附上該怎麼調。其餘全域修改是封閉集合的 amendment：`set_music_level`、`set_target`、
  `drop_beat`（整段拿掉，連同掛在上面的 B-roll 與配樂 cue）。
- **字幕綁素材時間，樣式綁專案**：一則 `SubtitleCue` 記的是「哪個檔、該檔第幾秒」，
  所以剪輯怎麼搬它都跟著走（搬 clip 字幕跟著搬、刪 clip 字幕跟著消失、切成兩半就在
  兩邊各出現一次）。`CaptionStyle` 則是專案的一個欄位，因為「這支要發到哪」是整支的事。
  預設集（`CAPTION_PRESETS`）裡的數字是**平台慣例不是量測**——各家 app 的按鈕與字卡
  蓋掉畫面的哪一塊、手機上字要多大才讀得清楚——所以收在一個地方，app 改版時改一次。
  `set_caption_style` 的 preset 是**起點不是鎖**：同時給的設定覆蓋在 preset 之上，
  而且是蓋在 preset 上而不是蓋在專案現有樣式上，否則指定一個平台會拿到跟上一個
  混了一半的結果。
  **一次一行**（`single_line`，預設開）：一句放不進一行就拆成幾行**依序**出現，而不是往上疊——
  疊起來的字幕塊會爬進畫面中間蓋住主體，也不是短影音的主流樣子。拆在**畫字幕的時候**
  （`one_line_each`，`build_ass` 與出界檢查共用）而不是存字幕的時候，因為同一組字幕可能
  出橫的也出直的，一行放得下幾個字要到那時才知道。有詞時間就在詞之間拆、每行在它第一個詞
  講出來時出現；沒有就依字數比例分時間。
  **斷在詞組的邊上**：每行填到滿會斷在 `下午2|點`、`一|整天`。所以在「最少放得下的行數」
  到「多三成」之間，用動態規劃挑成本最低的斷法——各行差不多長、斷點在停頓上、斷在語助詞
  （啊／了／吧…）之後或連接詞（但是／然後／那／我…）之前，不斷在數字後面，**絕不（高成本）
  斷在一個中文詞中間**。辨識器回來的中文是一個字一個詞，看不出 `營業` 從哪開始，所以用
  jieba 斷詞；它的詞典是簡體的，先用 OpenCC `t2s` 轉過（逐字對應，長度不變才用）再斷，
  `咖啡廳` 才會是一個詞。生成字幕（`_pieces`）與畫字幕用同一套斷法。
  沒有詞時間的字幕沒有停頓可以參考，只做平均分行。`generate_subtitles` 也照專案當下的樣式把一則字幕限制在一行寬，
  所以校對時看到的一則就是畫面上的一行；拆畫這一層是給「樣式或比例之後才換」的保險。
  雙語字幕不拆：第二語言屬於整句第一語言，拆了會對不上。
  **逐字動態需要詞的時間**，所以 `SubtitleCue` 帶 `words`（來源秒數，`place_cues`
  一併搬到時間軸秒數）。ASS 的 `\k` 是從 SecondaryColour 填到 PrimaryColour，
  所以開了逐字動態時兩個顏色才會不同——兩個一樣的話濾鏡照跑但畫面上什麼也看不出來。
  **改過字的字幕會丟掉詞時間**：時間描述的是舊的字，對著錯的音節亮起來比整句一起亮更糟。
  **講者標籤一律留著，要不要畫出來是樣式的事**。標籤由 `speaker_at` 用同一條八成規則
  算出來，所以字幕跟它所在的語意片段不可能認定成不同的人。顏色**依標籤排序指派**
  而不是依誰先講，否則重排一次剪輯再 render，兩個人的顏色會對調。
  沒有對到真名的標籤就照原樣印出來——`S2` 比把話安到別人頭上好。
- **重疊是兩個明確的例外**：同一軌的 clip 在**畫面**上不得重疊，這條沒變。
  `audio_lead` / `audio_lag` 讓一個 clip 的**聲音**伸出自己的畫面之外（J / L cut），
  `transition_in` 讓一個 clip 的**畫面**接進前一顆的尾巴（溶接、擦劃，或過一個顏色）。
  兩者都**不移動任何 clip**：剪點留在原地，多出來的媒體從 `source_range` 之外取，
  所以成片長度不變、後面的東西不用重排。`validate_project` 因此只擋畫面重疊，
  另外檢查這些延伸有沒有伸出檔案之外或時間軸之前，而淡入淡出改成對**聲音的長度**
  檢查而不是畫面的。
  builder 也因此改了兩條路徑：基礎軌的**聲音**從 concat 改成逐段定位再混音
  （concat 的語意就是「一段接一段」，表達不出重疊；定位用絕對樣本位置，
  長時間軸不會累積漂移），**畫面**則切成「直切的連續段」，段內 concat、段間 xfade。
  轉場**結束在剪點上**而不是跨過它——它吃掉的是自己的前導，所以時間軸長度不變。
  三種 kind 走同一條算術，差別只在 xfade 的名字，**除了 dip**：它是兩次混合中間夾一個
  顏色源，所以進場的 clip 只帶一半的前導（`Clip.run_up` 是唯一該問的地方）。
  前一半把離場的畫面混進顏色、交出一段長度剛好等於原時間軸的東西，後一半才是
  一般轉場那條算術，於是 offset 不必特別處理。xfade 要求兩邊 timebase 一致，
  而一段一顆的 run 帶的是幀率的、concat 過的 run 帶的是 muxer 的，所以全部先 `settb`，
  顏色源也一樣。
- **聲音的修復與拉齊是兩件事，而且都要人開口**：`Clip.cleanup` 是單一 clip 的修復
  （低頻轟隆、底噪嘶聲、齒音），三個各自獨立、預設全關——每一個都是靠丟掉錄音的一部分
  來運作的，而聽得出來的失敗是「洗到像在水裡」而不是「還有一點雜音」，所以設定一律偏保守。
  濾鏡接在**伸縮與音量之前**：降噪器是在對它拿到的東西建模，給它一段已經變速或已經壓小的
  聲音就是給錯東西。
  `EditPlan.level_voices` 則是整支的事：把每個人**往最小聲的那個拉齊**而不是往最大聲的，
  因為哪一個當基準對結果沒差（整體正規化會把差額補回來），但往下拉不可能爆音，
  往上拉會連那個人底下的嘶聲一起帶上來。
  一個視窗裡有兩個人講話時不動它——那一段不屬於任何一個人，套誰的 gain 都是選邊站，
  跟 `speaker_at` 遇到交接就不給標籤是同一條理由。
  **要不要拉齊是判斷，不是量測**：伺服器只回報兩個人差幾分貝（`VOICE_SPREAD_DB` 以上才說），
  開不開由 plan 決定。
- **另錄的旁白是自動處理的，不等人開口**：跟上一條相反，因為這裡的失敗不是品味——
  第一支實際剪出來的片子，相機收到的街聲比領夾麥收到的人聲**大十分貝**，兩軌都照原音量混，
  人聲整個被蓋掉；原本的 ducking 只有「配樂讓相機裡的人聲」一個方向。現在音軌若是旁白
  （`Track.voice`；沒講就在 render 時判斷：有逐字稿、句子蓋住那段錄音至少一半、且不是設成
  duck_under_speech 的配樂軌），render 時：旁白先拉到 `VOICE_KEY_DB`（-20 LUFS，直接用 ebur128
  量那幾段錄音——舊的分析沒有逐秒電平，而要修的正是那些已經剪好的片子），再用它當 sidechain
  把相機原音與疊在畫面上的聲音壓下去約 13 dB；配樂則同時讓相機裡的人聲與旁白。
  **不靠節拍分辨講話與音樂**：旁白單獨成檔會被當配樂跑節拍，音節是很強的 onset，
  那支開場配音量出 135.7 BPM；看的是逐字稿蓋了多少（它是九成，一首有歌詞的歌有前奏、間奏、尾奏）。
  相機原音**是壓低不是拿掉**，那是現場。聲音預覽裡旁白算在人聲那一側，現場算另一側，
  所以「現場有沒有讓開」看得到。匯出給別的軟體時 `left_behind` 會列出這一項。
- **轉場底下的聲音沒有自動柔化**，控制項本來就在：出場的 clip 給 `audio_fade_out`、
  進場的給 `audio_fade_in`。缺的是「多長、哪一邊」這個判斷，而那沒有語料訂不出來。
- **變速是一條貫通的鏈路**：`Clip.speed` 一改，`timeline_duration` 就變，
  `set_clip_speed` 預設 ripple 讓後面跟上。render 端畫面用 `setpts` 在 `fps` 正規化**之前**
  伸縮（之後做會把已經決定好的幀丟掉或重複），聲音的伸縮也**在補長截斷之前**——
  伸縮本身就是在決定長度。
  聲音有兩條路，由 `Clip.preserve_pitch` 選：`atempo` 在時域上伸縮、音高留在原處
  （人講話要的是這個），或 `asetrate` + `aresample` 改變取樣率再轉回來，讓音高隨速度
  升降（刻意的變調要的是這個）。`atempo` 單次只吃 0.5–2，所以超出的倍率拆成連乘。
  **`atempo` 之後一定要再 `aresample`**：它交出的串流時間讓後面負責定長的
  `apad` / `atrim` 讀錯，會把聲音截成四分之一、其餘補靜音——所以在補上這一段之前，
  任何帶變速的 clip render 出來幾乎是無聲的。`asetrate` 那條路徑結尾本來就有一個。
- **段落標記**：plan 的 `beats` 編譯時寫成 `Project.markers`，這樣「成片的形狀」
  才不是只存在於 plan 裡。編譯器只擁有自己做的那些（`from_beat_id` 有值），
  手加的原樣留著。被 `_merge` 併進前一顆的 beat，標記落在那顆合併鏡頭的開頭——
  近到可以合併的兩段就是同一顆鏡頭，標在鏡頭中間等於宣稱一個不存在的剪點。
- **背景工作**：render 與分析都跑在獨立 worker 子程序，狀態寫進 SQLite，
  所以伺服器重啟不會中斷工作，也能多行程共用同一個工作區。
- **記憶體閘門**：工作先排隊，不是呼叫就跑。`JobManager._plan` 在
  `Repository.update_active_jobs` 的單一 immediate transaction 內，一次看完所有未完成
  的工作再決定放行誰——所以多個伺服器或 worker 不會各自算出「還能再開一個」。
  判準有兩個：同時執行數（`CLIP_MCP_MAX_JOBS`）與剩餘實體記憶體減去保留量
  （`CLIP_MCP_MEMORY_RESERVE_MB`）。剛放行的工作還沒真的配置記憶體，所以 `WARMUP`
  之內它的估算值會額外從可用量扣除。排隊依先到先服務，不讓小工作一直插隊；
  但沒有任何工作在跑時，隊首一定放行——全部拒絕比慢慢跑更糟。
  worker 結束與 `get_job` 都會再推一次隊伍，所以不需要另外的排程器。
- **評測分層**：L1 是測試套件（算術對不對），L3 是判官評成片（還沒做）。
  `benchmark/` 是中間的 L2：**不 render**，直接拿編譯後的 windows 對語料的標註算分。
  五項底線（切到字、落在壞幀、長度誤差、必留覆蓋、必剔洩漏）全是純函式，
  所以同一份 plan 對同一批素材永遠得到同一個分數——分數掉了才算得上是證據。
  標註一律以**相對路徑 + 該檔秒數**錨定，不用 asset ID：asset ID 是每個工作區各自產生的，
  用它當錨點的語料換一台機器就什麼都量不到。
  這一層真正的陷阱是**「沒量到」和「量了沒事」在計分卡上長得一模一樣**：
  沒分析過的素材沒有字可以切到、沒有壞幀可以踩到，一刀剪過去兩項都是滿分。
  所以計分時一律檢查，把量不到的素材寫進 `Scorecard.unmeasured`，
  而且只要裡面有東西就不算 `clean`——沒測過的底線不能算通過。
  「有逐字稿但沒有詞級時間」也算量不到：那種素材每個剪點都會回報沒切到字。
- **skill 與程式碼同步**：`test_skill_resources.py` 雙向比對——每個工具與編輯操作都要在
  `SKILL.md` 裡提到，指南也不能提到不存在的操作，避免指南跟實作漂移。
